# Data Table

`Data Table` is a composition pattern, not a component exported by moduix. Use the semantic and
styled `Table` parts for markup, then use TanStack Table v9 for table state and data-grid behavior.
Keep records and table state in the screen or product feature that owns them, especially when that
state drives a route or server query. Columns, filters, row actions, and server contracts vary by
product, so keep that logic close to the feature that needs it.

The full block below is the interactive table shown on the home page. It demonstrates search,
sorting, column visibility, row selection, actions, and pagination. Copy the source and replace the
example records and actions with your product data.

## Start simple

| Need                                            | Start with                                                    |
| ----------------------------------------------- | ------------------------------------------------------------- |
| Read-only table                                 | The semantic [Table](/docs/table) component                   |
| Local sorting or filtering for a small dataset  | `Table` plus the matching TanStack row model                   |
| Server sorting, filtering, or pagination        | Controlled query state with the manual TanStack options below |
| Virtualized rows                                | Add virtualization only after measuring a real performance issue |

Use only the controls your table needs. Remove selection, column visibility, actions, or pagination
when users cannot use that capability.

The live previews use the React package. The source tabs show native React, Solid, and Vue implementations for TanStack Table v9.

## Basic

Declare the feature set with `tableFeatures()` and define typed `ColumnDef<typeof features, Payment>`
entries. React creates the instance with `useTable` and renders definitions with `flexRender`; Solid
uses `createTable` and `table.FlexRender`; Vue uses `useTable` and the `FlexRender` component with
`:header` or `:cell`. In every adapter, map header groups and visible cells into the moduix table anatomy.

The snippet renders visible columns and cells, so it registers `columnVisibilityFeature`. Add other
features only when the table needs them.

## Stable references

Keep `features`, records, and `columns` stable for the lifetime of the table. React and Solid declare
static inputs outside their components; Vue declares them once in `<script setup>`. In React, memoize
arrays derived from props or state instead of passing a new
reference to `useTable` on every render. In Solid, expose changing data through the reactive `data`
getter passed to `createTable`. In Vue, pass a `ref` or `computed` directly as `data`, not a one-time
`data.value` snapshot. See the TanStack
[FAQ](https://tanstack.com/table/latest/docs/faq) for the full explanation.

## Column widths

Use `TableColumnGroup` and `TableColumn htmlWidth` for columns whose width should stay stable.
Combine them with `table-layout: fixed` on the table root. The remaining column takes the available
space, while a changing sort icon cannot resize its column.

## Server data

When the API filters, sorts, or paginates records, keep those values in the feature's query state.
Pass the returned page to TanStack Table and turn off the corresponding client-side transforms.
This configuration replaces the client-side row models from the interactive example:

```ts
import { computed } from 'vue';

const features = tableFeatures({
  columnFilteringFeature,
  rowPaginationFeature,
  rowSortingFeature,
});

const table = useTable({
  features,
  data: computed(() => response.value.rows),
  columns,
  manualFiltering: true,
  manualPagination: true,
  manualSorting: true,
  rowCount: computed(() => response.value.rowCount),
  onColumnFiltersChange: (next) => {
    columnFilters.value = typeof next === 'function' ? next(columnFilters.value) : next;
  },
  onPaginationChange: (next) => {
    pagination.value = typeof next === 'function' ? next(pagination.value) : next;
  },
  onSortingChange: (next) => {
    sorting.value = typeof next === 'function' ? next(sorting.value) : next;
  },
  state: computed(() => ({
    columnFilters: columnFilters.value,
    pagination: pagination.value,
    sorting: sorting.value,
  })),
});
```

  </Tab>
</Tabs>

For server-owned behavior, do not add the matching `filteredRowModel`, `sortedRowModel`, or
`paginatedRowModel` to `features`: TanStack assumes that `response.rows` already reflects the query.
Pass `pageCount` instead of `rowCount` when that is what the API provides. `manualPagination` also
turns off the usual page reset, so reset `pagination.pageIndex` to `0` whenever a remote filter or
sort changes. Otherwise, the API can return an empty page. See TanStack's
[filtering](https://tanstack.com/table/latest/docs/guide/global-filtering),
[sorting](https://tanstack.com/table/latest/docs/guide/sorting), and
[pagination](https://tanstack.com/table/latest/docs/guide/pagination) guides for the query layer.

Render request state next to the table, not inside unrelated cells:

| Request state | Recommended result                                                              |
| ------------- | ------------------------------------------------------------------------------- |
| Initial load  | Keep column headers visible and show a labeled loading row or skeleton.         |
| Refetch       | Preserve current rows, expose a busy state, and prevent duplicate requests.     |
| Empty result  | Explain whether there are no records or filters removed every match.            |
| Error         | Keep the query controls available and offer a retry for the same query.          |

## Add features

TanStack Table is headless, so it does not provide the controls or layout for these features. Choose
the state and row models for the behavior that belongs to this specific data view instead of turning
every grid feature on by default.

| Need              | Add to this table                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Row actions       | Render a `Menu` in an actions column; keep action handlers in the product feature.                                                                                                                             |
| Row selection     | Control `rowSelection`, configure `getRowId` with a durable record ID, and render moduix `Checkbox` controls in a selection column.                                                                           |
| Column visibility | Control `columnVisibility` and expose `column.toggleVisibility()` through a `Menu`.                                                                                                                           |
| Server data       | Keep query state in the route or data layer. Use `manualFiltering`, `manualSorting`, and `manualPagination` only for transforms owned by the API, then pass response rows with `rowCount` or `pageCount`. |
| Large datasets    | Add virtualization to the table body only after measuring; keep the native `table`, `thead`, `tbody`, `tr`, `th`, and `td` semantics intact.                                                                     |

The TanStack Table [row models guide](https://tanstack.com/table/latest/docs/guide/row-models) lists
the available client-side transforms. The [row selection guide](https://tanstack.com/table/latest/docs/guide/row-selection)
explains controlled selection state and page-level selection, while the [React adapter](https://tanstack.com/table/latest/docs/framework/react/react-table)
documents `useTable`. The moduix [Table](/docs/table) page documents the rendered structure and its
styling hooks.

With `manualPagination`, keep the full `rowSelection` state for actions that span pages. TanStack's
selected-row models can only return records currently supplied to the table, even when the selection
state also contains IDs from other pages.

## Reuse

If the same product table appears in more than one place, extract its columns, toolbar, or pagination
controls into local feature components. Keep the resulting API product-specific. `PaymentsTable` is
more maintainable than a broad `DataTable` component that attempts to predict every filter, server
response, action, or selection rule.

## Accessibility

Keep the native table parts in the rendered output. Use `TableColumnHeader` for headers,
`TableCell` for data, and a short `TableCaption` when the surrounding heading does not identify the
data. Interactive controls inside cells need descriptive accessible names, and sortable headers
should expose their current direction through `aria-sort`. The filter input and selection controls in
the interactive example have explicit accessible names rather than relying on placeholder or icon
text.
