## Choosing the right component

Use `Dialog` for forms, confirmations, details, and secondary tasks that should keep the user in the
current page context. Use `Drawer` when the panel should remain attached to an edge of the viewport.

## Anatomy

```text
Dialog
├─ Dialog.Trigger
└─ Overlay content (automatically portalled)
   ├─ Dialog.Backdrop
   └─ Dialog.Positioner
      └─ Dialog.Content
         ├─ Dialog.CloseTrigger or Dialog.CloseIcon
         ├─ Dialog.Title
         ├─ Dialog.Description
         ├─ Dialog.Header (moduix layout helper)
         ├─ Dialog.Body (moduix layout helper)
         └─ Dialog.Footer (moduix layout helper)

Dialog.RootProvider
└─ the same automatically portalled content tree connected to moduix useDialog()

Dialog.Context
└─ a render function with the current dialog state and methods
```

| Part                     | Role                                                             |
| ------------------------ | ---------------------------------------------------------------- |
| `Dialog`                 | Owns the dialog's open state, focus lifecycle, and dismissal behavior. |
| `Dialog.Trigger`         | Opens the dialog.                                                |
| `Dialog.Backdrop`        | Optional modal backdrop layer.                                   |
| `Dialog.Positioner`      | Floating container that positions the content.                   |
| `Dialog.Content`         | Container for the dialog surface.                                |
| `Dialog.Title`           | Accessible dialog title.                                         |
| `Dialog.Description`     | Accessible supporting description.                               |
| `Dialog.CloseTrigger`    | Closes the dialog.                                               |
| `Dialog.Context`         | Renders children with the current dialog state and methods.      |
| `Dialog.RootProvider`    | Connects parts to state created with moduix `useDialog()`.       |

Import `useDialog()` when dialog state needs to live outside the rendered tree. Read that state in
reusable children with `Dialog.Context` or `useDialogContext()` from `@moduix/react`.

## Composition

The root automatically portals `Backdrop` and `Positioner`. Set `portalled={false}` to render them
inline, or pass `portalRef` to use a custom container. The structural parts stay explicit and can be
styled individually.

### Recommended composition

Keep `Backdrop`, `Positioner`, and `Content` explicit. This gives you structural override points and
keeps the composition aligned with Ark UI. Leave out `Backdrop` for non-modal dialogs.

Use `Dialog.Trigger asChild` and `Dialog.CloseTrigger asChild` with a single semantic button child.
`Dialog.CloseIcon` is a moduix helper that combines Ark `CloseTrigger` with the library close button.

### When to go custom

Use `open` with `onOpenChange(details)` when React should control the dialog state. The callback
receives an Ark detail object, so read `details.open`.

Use moduix `useDialog()` with `Dialog.RootProvider` when state and methods need to live outside the
rendered dialog tree. Do not render a second `Dialog` for the same store.

Use `ids` when separately composed parts need stable, shared accessibility IDs. Use `initialFocusEl`
and `finalFocusEl` to choose explicit focus targets. Use `role="alertdialog"` for destructive or
critical confirmation flows.

Use `lazyMount` and `unmountOnExit` instead of conditionally rendering the root. Set `present` only
when a JavaScript-controlled exit animation needs to control whether the content stays mounted.

### Default props

By default, portalled overlay content mounts lazily and unmounts after its exit animation. Set
`unmountOnExit={false}` to keep it mounted after the first open. Set both lifecycle props to `false`
only when eager initial rendering is needed.

| Surface                  | Default | Notes                                                  |
| ------------------------ | ------- | ------------------------------------------------------ |
| `Dialog`                 | -       | No additional behavioral defaults; Ark defaults apply. |

### Behavioral notes

- Modal dialogs trap focus, prevent background scrolling, hide the content behind the dialog from
  assistive technology, and restore focus after close.
- `modal={false}` disables focus trapping and scroll prevention. Leave out the backdrop in this mode.
- `closeOnEscape`, `closeOnInteractOutside`, `trapFocus`, `preventScroll`, `restoreFocus`,
  `persistentElements`, and the outside-interaction callbacks pass through to Ark UI.
- `Dialog.Title` or a root `aria-label` is required to give the dialog an accessible name.
- When the user prefers reduced motion, Dialog shortens its entry and exit animations while
  preserving Ark UI's presence lifecycle.
- Every rendered close part needs a unique ID. The canonical Basic composition uses one
  `Dialog.CloseIcon`; if a dialog needs multiple close controls, give the additional parts explicit
  unique `id` values.
- Nested content receives `data-has-nested` and `--nested-layer-count`. moduix uses these hooks to
  scale the parent down and offset it downward so the active nested dialog still reads as a separate layer.
- The menu and rapid-state-change examples use the controlled `open` contract. Unsaved-change
  confirmation uses two moduix `useDialog()` stores and intercepts the parent store's `onOpenChange`.

### Styling hooks

- moduix slots: `dialog-trigger`, `dialog-backdrop`, `dialog-positioner`, `dialog-content`,
  `dialog-title`, `dialog-description`, `dialog-close-trigger`, `dialog-close-icon`,
  `dialog-header`, `dialog-body`, and `dialog-footer`.
- Ark anatomy: `data-scope="dialog"` with `data-part="trigger|backdrop|positioner|content|title|description|close-trigger"`.
- State: `data-state="open|closed"`, `data-has-nested`, `data-nested`, `data-current`, and
  `data-value`.
- Runtime variables: `--layer-index` and `--nested-layer-count`.
- `Dialog.CloseIcon` is absolutely positioned against `Dialog.Content`; its placement does not
  depend on `Dialog.Header`.
