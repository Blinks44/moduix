## Choosing the right component

`FocusTrap` is a low-level utility for managing focus. Use it when your application owns a custom interactive
surface and needs keyboard focus to stay inside that surface until a task is complete or the user explicitly leaves it.

Use `Dialog` for a modal window and `Drawer` for a modal panel attached to the edge of the viewport. Both already
handle focus trapping, focus restoration, scroll prevention, dismissal, and dialog semantics. Do not add `FocusTrap`
inside either component.

`FocusTrap` comes from Ark UI, so import it from there. moduix does not re-export or style this utility:

```tsx
import { FocusTrap } from '@ark-ui/react/focus-trap';
```

If these packages are not dependencies in your app yet, install them with:

```bash
pnpm add @ark-ui/react @moduix/react
```

## Focus lifecycle

### Choosing initial focus

By default, the first tabbable element inside the trap receives focus when the trap is activated. An element with the
`autofocus` attribute is also respected. In React, use the `autoFocus` prop for this attribute. Use `initialFocus` when
another element, such as the main input or primary action, should receive focus first.

Set `initialFocus={false}` when activation should not move focus at all. This also prevents `fallbackFocus` from being
used during activation.

### Handling an empty surface

If the trapped surface has no tabbable elements, provide `fallbackFocus`. Give the fallback target `tabIndex={-1}` so
Ark can focus it programmatically. When `initialFocus` is not `false`, activation throws an error if it cannot find a
tabbable element or a fallback target.

### Restoring focus

By default, focus returns to the element that was focused before the trap was activated. Set
`returnFocusOnDeactivate={false}` when another part of the workflow owns focus after deactivation. Use
`setReturnFocus` to replace the default target with an element or a function that returns one. You can also set it to
`false` to skip focus restoration.

The `onActivate` and `onDeactivate` callbacks run before Ark moves focus to the next target. Use them for side effects,
not as a replacement for the focus lifecycle.

### Including portalled content

If interactive content is rendered in a portal outside the trapped surface, pass functions that return those elements to
`persistentElements` so Ark treats that content as part of the trap. Keep related focusable content inside the trapped
surface when possible.

### Using a custom root

By default, `FocusTrap` renders a wrapper around its children. Set `asChild` to apply the trap to one child element when
your own element must be the container. Use a single semantic element as the child.

## What FocusTrap does not do

`FocusTrap` manages keyboard focus only. It does not render a backdrop or portal, add a dialog role or accessible name,
make the rest of the page inert, block scrolling, handle Escape, or dismiss the surface after outside interaction.

Add those behaviors yourself for a custom modal surface, or use `Dialog` or `Drawer` when their complete interaction
model fits the task.

## Using moduix

Place `Card`, `Button`, `Stack`, and other moduix controls inside the trap as usual. Give the surface a clear heading
and description, and provide a visible action that releases the trap. Never trap focus in content that the user cannot
dismiss.

If the surface is a modal dialog or drawer, use the corresponding moduix component instead of assembling the modal
behavior around `FocusTrap`.

## Ownership

Ark UI owns `FocusTrap` and its focus lifecycle API. moduix supplies the surrounding controls and documents how to
combine them, but it does not re-export or style `FocusTrap`.
