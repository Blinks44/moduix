## Choosing the right component

Use `PasswordInput` when a sensitive value should stay hidden by default but can be shown when
needed.

- Choose **`Input`** for plain text-like fields without a visibility toggle.
- Choose **`PasswordInput`** for passwords, API keys, and other secure strings.
- Choose **`InputGroup`** when the field needs a custom inline action that is not password visibility.

## Anatomy

```text
PasswordInput / PasswordInput.Root
├─ PasswordInput.Label
└─ PasswordInput.Field
   └─ PasswordInput.Control
      ├─ PasswordInput.Input
      └─ PasswordInput.VisibilityTrigger
         └─ PasswordInput.Indicator

PasswordInput.RootProvider
└─ same tree connected to a usePasswordInput() state object
```

| Part                                   | Role                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------ |
| `PasswordInput` / `PasswordInput.Root` | Root part that owns password visibility and field state.                      |
| `PasswordInput.RootProvider`           | Connects the parts to state created with `usePasswordInput()`.                |
| `PasswordInput.Context`                | Render-prop access to the root state.                                         |
| `PasswordInput.Label`                  | Labels the input and reflects required, disabled, invalid, and read-only states. |
| `PasswordInput.Field`                  | Convenience composition of the control, input, visibility trigger, and indicator. |
| `PasswordInput.Control`                | Groups the input and visibility trigger together.                              |
| `PasswordInput.Input`                  | Native input whose `type` switches between `password` and `text`.             |
| `PasswordInput.VisibilityTrigger`      | Button that toggles visibility.                                                |
| `PasswordInput.Indicator`              | Shows content for the visible or hidden state; moduix supplies default icons.  |

## Composition

`PasswordInput.Field` is the convenience composition for the control, input, visibility trigger,
and indicator. Replace it with `Control`, `Input`, `VisibilityTrigger`, and `Indicator` when the
structure, input props, icons, or part-level styling must differ.

Keep visibility state on the root. Use `defaultVisible` for an uncontrolled initial state, or pair
`visible` with `onVisibilityChange(details)` when application state owns visibility. Use
`usePasswordInput()` with `PasswordInput.RootProvider` when a sibling or external control needs the
same state.

Pass value props such as `value`, `defaultValue`, `placeholder`, and `onInput` or `onChange` to
`PasswordInput.Input`. The native input participates in form submission and reset, so pass `name`
to `PasswordInput`; this component does not render a separate `HiddenInput`.

## Styling

CSS Modules packages expose `--moduix-password-input-*` variables for the control shell, input area,
and visibility trigger on top of the shared `Input` styles. Tailwind packages use utility classes
and consumer classes instead of mirroring these component variables.

### Styling hooks

- The root and root provider expose `data-slot="password-input-root"` and
  `data-slot="password-input-root-provider"`.
- Ark parts keep `data-scope="password-input"` and `data-part` values for `root`, `label`, `control`,
  `input`, `visibility-trigger`, and `indicator`.
- Use `data-state="visible" | "hidden"` on the input, trigger, and indicator for visibility styles.
  Use `data-disabled`, `data-invalid`, `data-readonly`, and `data-required` where Ark provides them.
  The control receives the disabled, invalid, and read-only state attributes used by the field shell.
- Ark does not expose component-specific CSS variables at runtime; moduix adds
  `--moduix-password-input-*` variables for CSS Modules visual defaults.
