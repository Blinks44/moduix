Use `ClientOnly` when a browser-dependent subtree should stay out of server rendering while a fallback keeps its
place in the layout.

## Render browser-dependent content

During server rendering and until hydration is complete, `ClientOnly` renders `fallback`. It then renders its children
on the client. Use it for code that reads `window`, `document`, `navigator`, storage, layout measurements, or a
browser-only library.

## Keep browser APIs inside the boundary

`ClientOnly` controls when its child subtree is rendered. It does not turn the parent component or its module into a
client-only module. Keep browser-global reads inside the child rendered by `ClientOnly`, or inside an effect or event
handler. If your application framework requires a separate client boundary, add that boundary according to its own
rules.

Do not read browser globals while creating `fallback`. The fallback must be safe to render on the server and should
resemble the final content closely enough to avoid a layout shift.

## Integration and accessibility

No provider, router, or root-layout registration is required. Render the boundary where the browser-dependent region
belongs.

Give the fallback approximately the same dimensions as the final content. In the recipe, `aria-busy="true"` marks the
temporary card as busy and the loading `Skeleton` remains decorative. Do not put duplicate interactive controls in a
fallback if users cannot activate them until hydration.
