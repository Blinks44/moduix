# Composition Patterns

moduix keeps Ark composition visible. Instead of folding behavior into one large prop surface, most
components expose the stateful root and the parts that own semantics, layout, and styling.

That gives you a predictable customization ladder:

- use the shipped parts directly
- re-export them behind product-specific names
- wrap only the parts that need repeated product styling or layout

These patterns stay the same whether you consume `@moduix/react` or install source through the
registry.

## Choose an install

Use the npm package for package-managed updates, component imports from
`@moduix/react/*`, and styles from `@moduix/react/style.css`.

Use the `shadcn` registry when you want to own the component source files inside your application. It writes
the selected component and its required moduix styles, icons, and utilities into your project, so you
can change them directly and import them from `@/components/moduix/*`.

Copy-owned components do not receive package updates automatically. When a newer moduix version is
available, add it through `shadcn`, then review and merge the resulting diff on your terms. Follow the
[Quick start](/docs/quick-start#install-with-the-shadcn-cli) for the one-time registry setup
and component commands.

## Use the part tree

Before creating wrappers, start with the part tree documented on the component page. Use `className`, CSS variables,
`data-slot`, and Ark state attributes on the parts that actually own those responsibilities.

Root-only exports such as `Popover`, `Tooltip`, and `Select` are the short form of `*.Root`.
Popup-like and dialog-like roots portal their overlay subtree automatically, so the structure stays
visible without adding a separate `Portal` wrapper.

For example:

```text
Dialog / Dialog.Root
├─ Dialog.Trigger
├─ Overlay subtree (automatically portalled)
│  ├─ Dialog.Backdrop
│  └─ Dialog.Positioner
│     └─ Dialog.Content
│        ├─ Dialog.Title
│        ├─ Dialog.Description
│        └─ Dialog.CloseTrigger
```

Use `portalled={false}` for inline rendering and `portalRef` for a custom container when the
component supports those props. Use `Dialog.RootProvider` as the alternative state entry point when
the state object lives outside the rendered subtree.

## Structural parts

Not every primitive exposes every part below. Start from the component page's anatomy, then keep the
parts it documents visible when your product needs to override them.

| Part         | Responsibility                                                                 |
| ------------ | ------------------------------------------------------------------------------ |
| `Backdrop`   | Provides modal separation and outside-interaction targeting.                   |
| `Positioner` | Owns viewport or anchored placement and scrolling behavior.                    |
| `Content`    | Renders the interactive surface and receives state attributes.                 |
| `Arrow`      | Connects anchored popup content to its trigger when the primitive supports it. |

Do not hide these nodes inside product wrappers unless your product contract intentionally removes
their override points.

## `asChild`

Use `asChild` when another semantic element should own the DOM node while a moduix part attaches its behavior to it.

```tsx
import { Button } from '@moduix/react/button';
import { Popover } from '@moduix/react/popover';
// shadcn copy-owned: import { Button } from '@/components/moduix/button';
// shadcn copy-owned: import { Popover } from '@/components/moduix/popover';

export function FiltersPopover() {
  return (
    <Popover positioning={{ gutter: 8 }}>
      <Popover.Trigger asChild>
        <Button variant="outline">Filters</Button>
      </Popover.Trigger>
      <Popover.Positioner>
        <Popover.Content>Choose one or more filters.</Popover.Content>
      </Popover.Positioner>
    </Popover>
  );
}
```

Keep a single semantic child that can receive Ark props. If the child component swallows refs,
event handlers, or attributes, `asChild` will not behave correctly.

## `ids`

Most compositions wire their own relationships automatically. Share `ids` only when two primitives must point at the
same trigger or description node, share IDs instead of hand-writing aria relationships.

```tsx
import { Avatar } from '@moduix/react/avatar';
import { Tooltip } from '@moduix/react/tooltip';
import { useId } from 'react';

export function AssigneeTooltip() {
  const id = useId();

  return (
    <Tooltip ids={{ trigger: id }}>
      <Tooltip.Trigger asChild>
        <Avatar ids={{ root: id }}>
          <Avatar.Fallback name="Sam Ortiz" />
        </Avatar>
      </Tooltip.Trigger>
      <Tooltip.Body>Sam Ortiz is online</Tooltip.Body>
    </Tooltip>
  );
}
```

This keeps the accessibility wiring in Ark instead of duplicating `aria-*` attributes by hand.

## Re-export first

If your product needs shorter imports or a branded surface, start with re-exports before writing
new abstractions. Re-exporting keeps the original behavior intact while giving your application a
stable local API.

```tsx
import { Dialog as ModuixDialog } from '@moduix/react/dialog';
// shadcn copy-owned: import { Dialog as ModuixDialog } from '@/components/moduix/dialog';

export const Dialog = ModuixDialog;
export const DialogTrigger = ModuixDialog.Trigger;
export const DialogBackdrop = ModuixDialog.Backdrop;
export const DialogPositioner = ModuixDialog.Positioner;
export const DialogContent = ModuixDialog.Content;
export const DialogTitle = ModuixDialog.Title;
export const DialogDescription = ModuixDialog.Description;
export const DialogCloseTrigger = ModuixDialog.CloseTrigger;
```

This is the lowest-risk customization path:

- consumers import from your product layer instead of directly from `@moduix/react/*` or
  `@/components/moduix/*`
- Ark behavior stays untouched
- moving from package usage to copy-owned usage stays straightforward
- wrappers can be added later only where they are actually needed

## Add a product contract

Give the product contract only to the part that owns the decision. The local `Dialog` is a complete product boundary:
consumers import one component and use
`Dialog.Trigger`, `Dialog.Content`, and every other part from it. Internally, only the dialog surface
adds the small `tone` contract because it owns the visual decision.

Consumers now import only the product component:

```tsx
import { Dialog } from '@/components/ui/dialog';

export function DeleteProjectDialog() {
  return (
    <Dialog>
      <Dialog.Trigger>Delete project</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content tone="danger">
          <Dialog.Header>
            <Dialog.Title>Delete this project?</Dialog.Title>
            <Dialog.CloseIcon />
            <Dialog.Description>This cannot be undone.</Dialog.Description>
          </Dialog.Header>
          <Dialog.Footer>
            <Dialog.CloseTrigger>Cancel</Dialog.CloseTrigger>
          </Dialog.Footer>
        </Dialog.Content>
      </Dialog.Positioner>
    </Dialog>
  );
}
```

The product root preserves the complete moduix API. Its custom `Dialog.Content` forwards `ref`,
`className`, and every existing content prop. The `data-dialog-tone` attribute is a product styling
hook; the CSS maps it through public dialog variables instead of copying the component's styles.

Keep the part tree explicit: `Dialog.Backdrop`, `Dialog.Positioner`, and `Dialog.Content` still make
overlay behavior and styling ownership easy to find. Add a wrapper only when it represents a repeated
product decision, not for a one-off class name.

## External state

Move state outside the tree only when its ownership changes, and keep Ark detail objects intact. For example, dialog
open state still uses
`onOpenChange(details)` and reads `details.open`.

Use component state helpers only when state needs to live outside the rendered subtree:

- `Component.Context` for one-off inline reads
- `useComponentContext()` inside descendants that already live under the root
- `useComponent()` plus `Component.RootProvider` when state is created outside the rendered tree

```tsx
import { Dialog, useDialog } from '@moduix/react/dialog';

export function DialogFromExternalState() {
  const dialog = useDialog();

  return (
    <Dialog.RootProvider value={dialog}>
      <Dialog.Trigger>Open dialog</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content>State is owned by useDialog().</Dialog.Content>
      </Dialog.Positioner>
    </Dialog.RootProvider>
  );
}
```

Do not render `Root` and `RootProvider` for the same state instance.

## Choose a level

- Only need usage? Stay on the shipped parts.
- Need product import paths? Re-export first.
- Need repeated product visuals? Wrap the specific parts that own those visuals.
- Need different behavior? Drop to the explicit part tree instead of inventing new top-level props.
