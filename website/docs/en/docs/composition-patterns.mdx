# Composition Patterns

`moduix` keeps Ark's composition model visible. Most components expose a stateful root and separate
parts for structure, semantics, and styling. This makes it clear which layer owns each responsibility
and gives you a predictable way to customize a component:

- use the shipped parts directly;
- re-export them from your product layer;
- wrap only the parts that need repeated product styling or layout.

The same approach works with `@moduix/react` and with source code copied from the registry.

## Choose an install

Choose the npm package when you want your package manager to handle updates. Import components from
`@moduix/react/*` and the shared styles from `@moduix/react/style.css`.

Choose the `shadcn` registry when your application should own the component source. It copies the
selected component and its required moduix styles, icons, and utilities into your project. You can
then change that code directly and import it from `@/components/moduix/*`.

Components whose source lives in your application do not receive package updates automatically. When
a new moduix version is available, add the component again through `shadcn`, then review and merge
the resulting diff. Follow the [Quick start](/docs/quick-start#install-with-the-shadcn-cli) for the
one-time registry setup and component commands.

## Use the part tree

Before creating wrappers, start with the part tree on the component page. Apply `className`, CSS
variables, `data-slot`, and Ark state attributes to the parts that actually own those responsibilities.

Root exports such as `Popover`, `Tooltip`, and `Select` are shortcuts for `*.Root`. For dialog-like
and popup components, the root automatically portals the overlay subtree, so the structure remains
explicit without a separate `Portal` wrapper.

For example:

```text
Dialog / Dialog.Root
├─ Dialog.Trigger
├─ Overlay subtree (automatically portalled)
│  ├─ Dialog.Backdrop
│  └─ Dialog.Positioner
│     └─ Dialog.Content
│        ├─ Dialog.Title
│        ├─ Dialog.Description
│        └─ Dialog.CloseTrigger
```

Use `portalled={false}` for inline rendering and `portalRef` for a custom container when the
component supports those props. Use `Dialog.RootProvider` when the state object is created outside
the rendered tree.

## Structural parts

Not every primitive exposes every part below. Start with the anatomy on the component page, then keep
the parts it documents visible when your product needs to override them.

| Part         | Responsibility                                                                    |
| ------------ | ------------------------------------------------------------------------------- |
| `Backdrop`   | Separates a modal surface from the rest of the page and receives outside interactions. |
| `Positioner` | Owns viewport or anchored placement and scrolling behavior.                       |
| `Content`    | Renders the interactive surface and receives state attributes.                    |
| `Arrow`      | Connects anchored popup content to its trigger when the primitive supports it.   |

Do not hide these nodes inside product wrappers unless your product contract intentionally removes
their override points.

## `asChild`

Use `asChild` when an existing semantic element should be the DOM node and a moduix part should only
add its behavior to that element.

```tsx
import { Button } from '@moduix/react/button';
import { Popover } from '@moduix/react/popover';
// shadcn copy-owned: import { Button } from '@/components/moduix/button';
// shadcn copy-owned: import { Popover } from '@/components/moduix/popover';

export function FiltersPopover() {
  return (
    <Popover positioning={{ gutter: 8 }}>
      <Popover.Trigger asChild>
        <Button variant="outline">Filters</Button>
      </Popover.Trigger>
      <Popover.Positioner>
        <Popover.Content>Choose one or more filters.</Popover.Content>
      </Popover.Positioner>
    </Popover>
  );
}
```

Keep one semantic child that can receive Ark props. If the child component swallows refs, event
handlers, or attributes, `asChild` will not behave correctly.

## `ids`

Most compositions create their own relationships automatically. Use `ids` when two primitives need
to coordinate a stable ID, such as when they share the same trigger element. Do not write the ARIA
relationships by hand.

```tsx
import { Avatar } from '@moduix/react/avatar';
import { Tooltip } from '@moduix/react/tooltip';
import { useId } from 'react';

export function AssigneeTooltip() {
  const id = useId();

  return (
    <Tooltip ids={{ trigger: id }}>
      <Tooltip.Trigger asChild>
        <Avatar ids={{ root: id }}>
          <Avatar.Fallback name="Sam Ortiz" />
        </Avatar>
      </Tooltip.Trigger>
      <Tooltip.Body>Sam Ortiz is online</Tooltip.Body>
    </Tooltip>
  );
}
```

This keeps the accessibility wiring in Ark instead of duplicating `aria-*` attributes manually.

## Re-export first

If your product needs shorter imports or a branded API, start with re-exports before writing new
abstractions. Re-exports preserve the original behavior while giving your application a stable local
API.

```tsx
import { Dialog as ModuixDialog } from '@moduix/react/dialog';
// shadcn copy-owned: import { Dialog as ModuixDialog } from '@/components/moduix/dialog';

export const Dialog = ModuixDialog;
export const DialogTrigger = ModuixDialog.Trigger;
export const DialogBackdrop = ModuixDialog.Backdrop;
export const DialogPositioner = ModuixDialog.Positioner;
export const DialogContent = ModuixDialog.Content;
export const DialogTitle = ModuixDialog.Title;
export const DialogDescription = ModuixDialog.Description;
export const DialogCloseTrigger = ModuixDialog.CloseTrigger;
```

This is the lowest-risk customization path:

- consumers import from your product layer instead of directly from `@moduix/react/*` or
  `@/components/moduix/*`;
- Ark behavior stays untouched;
- moving from package usage to source-owned usage stays straightforward;
- wrappers can be added later only where they are actually needed.

## Add a product contract

Give a product contract only to the part that owns the decision. The local `Dialog` becomes a complete
product boundary: consumers import one component and use `Dialog.Trigger`, `Dialog.Content`, and the
other parts from it. Internally, only the dialog surface adds the small `tone` contract because it owns
the visual decision.

Consumers now import only the product component:

```tsx
import { Dialog } from '@/components/ui/dialog';

export function DeleteProjectDialog() {
  return (
    <Dialog>
      <Dialog.Trigger>Delete project</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content tone="danger">
          <Dialog.Header>
            <Dialog.Title>Delete this project?</Dialog.Title>
            <Dialog.CloseIcon />
            <Dialog.Description>This cannot be undone.</Dialog.Description>
          </Dialog.Header>
          <Dialog.Footer>
            <Dialog.CloseTrigger>Cancel</Dialog.CloseTrigger>
          </Dialog.Footer>
        </Dialog.Content>
      </Dialog.Positioner>
    </Dialog>
  );
}
```

The product root preserves the complete moduix API. Its custom `Dialog.Content` forwards `ref`,
`className`, and every existing content prop. The `data-dialog-tone` attribute is a product styling
hook; the CSS maps it to public dialog variables instead of copying the component's styles.

Keep the part tree explicit: `Dialog.Backdrop`, `Dialog.Positioner`, and `Dialog.Content` make overlay
behavior and styling ownership easy to find. Add a wrapper only when it represents a repeated product
decision, not for a one-off class name.

## External state

Move state outside the tree only when its ownership changes, and keep Ark detail objects intact. For
example, dialog open state still uses `onOpenChange(details)` and reads `details.open`.

Use the component's state APIs according to where you need access:

- `Dialog.Context` for a one-off read in the render tree;
- `useDialogContext()` inside reusable descendants that already live under the root;
- `useDialog()` with `Dialog.RootProvider` when state is created outside the rendered tree.

```tsx
import { Dialog, useDialog } from '@moduix/react/dialog';

export function DialogFromExternalState() {
  const dialog = useDialog();

  return (
    <Dialog.RootProvider value={dialog}>
      <Dialog.Trigger>Open dialog</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content>State is owned by useDialog().</Dialog.Content>
      </Dialog.Positioner>
    </Dialog.RootProvider>
  );
}
```

Do not render `Root` and `RootProvider` for the same state instance.

## Choose a level

- Need only the standard usage? Stay with the shipped parts.
- Need product-specific import paths? Re-export first.
- Need repeated product visuals? Wrap the specific parts that own those visuals.
- Need different behavior? Use the explicit part tree instead of inventing new top-level props.
