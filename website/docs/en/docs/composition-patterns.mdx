# Composition Patterns

Moduix keeps Ark's part-based composition visible. Start with the shipped parts, re-export them when
your application needs stable local imports, and add a wrapper only when it represents a repeated
product decision.

The same ownership model applies to every shipped framework adapter, whether components come from an npm package or
the shadcn registry. Framework tabs below show only the mechanics that actually differ.

## Choose an ownership level

| Need | Start with |
| --- | --- |
| Standard component behavior | Shipped Moduix parts |
| Product-owned import paths | Direct re-exports |
| Repeated visual or layout rule | A focused wrapper around the part that owns it |
| State outside the rendered tree | `use<Component>()` with `<Family>RootProvider` |

Choose the lowest level that solves the repeated need. A one-off class or callback does not justify a
new component API.

## Start with the part tree

Read the anatomy on the component page before writing a wrapper. Keep structural parts visible so
placement, scrolling, focus, and styling ownership remain easy to find.

```text
Dialog
├─ DialogTrigger
└─ Overlay subtree, automatically portalled
   ├─ DialogBackdrop
   └─ DialogPositioner
      └─ DialogContent
         ├─ DialogTitle
         ├─ DialogDescription
         └─ DialogCloseTrigger
```

Use `portalled={false}` for inline rendering and `portalRef` for a custom container when the component
supports those props. Use `DialogRootProvider` only when dialog state was created outside the rendered tree.

## Compose a semantic child

Use `asChild` when an existing element should remain the DOM node and a Moduix part should add only
its behavior. React accepts a single child element. Solid accepts a render function and requires Ark
props to be spread onto the returned element.

## Re-export before wrapping

Re-exports give the application a stable product import without changing behavior. Import the native
adapter and expose only the names your product wants to support:

<Tabs groupId="framework">
  <Tab label="React" value="react">

```tsx
import { Dialog, DialogContent, DialogTrigger } from '@moduix/react/dialog';

export { Dialog, DialogTrigger, DialogContent };
```

  </Tab>
  <Tab label="Solid" value="solid">

```tsx
import { Dialog, DialogContent, DialogTrigger } from '@moduix/solid/dialog';

```

  </Tab>
</Tabs>

This keeps a later move between package imports and source-owned registry imports straightforward.

## Move state only when ownership changes

Use `DialogContext` for a one-off read inside the tree. Use `useDialogContext()` in reusable descendants.
Create state with `useDialog()` and connect it through `DialogRootProvider` only when controls outside
the dialog need the same state.

Do not render `Dialog` and `DialogRootProvider` for the same state instance. Keep Ark detail objects intact,
such as `onOpenChange(details)` and `details.open`.

## Review the boundary

- Keep `DialogBackdrop`, `DialogPositioner`, `DialogContent`, and other meaningful parts visible.
- Prefer public CSS variables and state attributes over copied internal styles.
- Forward every native prop and framework-specific ref contract your wrapper accepts.
- Add a custom prop only for a repeated product decision.
- Test keyboard interaction, focus return, portals, and controlled state after wrapping.
