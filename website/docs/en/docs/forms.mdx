# Forms

Moduix provides accessible fields, controls, and native form participation. Start with a native
`<form>` and add a state library only when validation, repeated fields, or submission state requires
one.

## Framework support

Choose a library that ships a native adapter for your framework. The documentation currently covers
the Moduix adapters that are available today:

| Approach        | React | Solid | Best fit                                      |
| --------------- | ----- | ----- | --------------------------------------------- |
| Native form     | Yes   | Yes   | Small forms and browser-managed validation.  |
| Formisch        | Yes   | Yes   | Valibot schemas and compact reactive state.  |
| React Hook Form | Yes   | No    | React forms with an uncontrolled-first API.  |
| TanStack Form   | Yes   | Yes   | Explicit controlled state and typed workflows. |

React Hook Form is intentionally documented only for React. Solid applications should use a native
form, Formisch, or TanStack Form instead of adapting a React hook through a compatibility layer.

## Core rules

1. Wrap one control in `Field` when it needs a label, helper text, error text, or shared state.
2. Use `Fieldset` for a related group with one visible legend.
3. Keep labels visible and give every submitted control a `name`.
4. Pass `invalid`, `required`, `disabled`, and `readOnly` through the Moduix field or control root.
5. Render each required native form part exactly once.

| Component      | Native form part                                                   |
| -------------- | ------------------------------------------------------------------ |
| `Checkbox`     | `HiddenInput`                                                       |
| `RadioGroup`   | `ItemHiddenInput` for every explicitly composed item               |
| `SegmentGroup` | `ItemHiddenInput` for every explicitly composed item               |
| `Select`       | `HiddenSelect`                                                      |
| `Slider`       | `HiddenInput` for every submitted thumb                            |
| `DateInput`    | Indexed `HiddenInput` parts when a range needs separate names      |
| `SignaturePad` | `HiddenInput` with an application-defined serialized `value`       |
| Other Ark controls with a hidden part | The matching `HiddenInput` inside the root       |

Do not register or render a second hidden input for the same value. `Combobox` keeps its form name
on the root and does not need an additional hidden part.

## Validation and reset

Keep native constraints such as `required`, `minLength`, `pattern`, `min`, and `max` when browser
validation owns the flow. When a library owns visible errors, add `noValidate`, pass its result to
`Field invalid`, and render a clear `FieldErrorText` only after the chosen validation lifecycle has
found a problem.

Native `type="reset"` and `form.reset()` restore uncontrolled controls. For library-controlled
fields, use the library's reset API so its state and the Moduix values stay synchronized.

Move invalid-submit focus to the real focusable element: `Input`, `Textarea`, `SelectTrigger`, or
`ComboboxInput`. The integration guide for each library describes whether focus is automatic or
application-owned.

## Submission and server errors

Keep ready, submitting, error, and success states explicit. Prevent duplicate requests while an
asynchronous submission is pending, keep entered values visible after a failure, and leave a clear
retry path.

Map a server error about one value to that field's `FieldErrorText`. Render request or permission
failures that do not belong to a field as a form-level `role="alert"`. Repeated fields should use
stable item IDs so values, focus, and errors do not move when another row is removed.

`FormData` values are strings or `File` objects, and repeated names produce repeated entries. Always
normalize and validate submitted data again at the server boundary. For the underlying Ark behavior,
see the [Ark UI forms guide](https://ark-ui.com/docs/guides/forms).
