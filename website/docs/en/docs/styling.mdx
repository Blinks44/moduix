# Styling

Moduix ships separate CSS Modules and Tailwind packages for every current framework adapter. Choose
the styling track your application already uses, then make each change at the highest layer that owns
the decision.

This guide assumes the matching package and stylesheet are already configured through
[Quick start](/docs/quick-start).

## Choose a styling track

| Track | React | Solid | Best fit |
| --- | --- | --- | --- |
| CSS Modules | `@moduix/react` | `@moduix/solid` | Shipped component styles with token and local-class overrides |
| Tailwind CSS | `@moduix/react-tailwind` | `@moduix/solid-tailwind` | Utility-backed components in an existing Tailwind v4 application |

CSS Modules and Tailwind are equal distribution paths, not layers to combine on the same component.
Use the package that matches both your framework and styling track.

## Choose where to make a change

| Goal | Preferred surface |
| --- | --- |
| Adopt a complete visual direction | A curated [Theme preset](/docs/themes) |
| Change a system-wide color, size, radius, or gap | A semantic token from [Tokens](/docs/tokens) |
| Keep a component family aligned | A shared family token |
| Make one CSS Modules component intentionally different | A documented component variable |
| Style one product composition | Consumer classes on the parts that own the visuals |

Start with tokens for system decisions. Move to a rendered part only when the decision belongs to one
composition.

## Style exported parts

Apply the consumer class to the part that owns the visual change. Combine it with Ark state attributes
such as `data-state` or `data-disabled` for stateful styles. Do not depend on generated class names or
DOM order.

## Target hidden parts carefully

When a product wrapper intentionally hides an inner part, use its stable `data-slot` as an escape
hatch:

```css
.root {
  [data-slot='accordion-item-trigger'] {
    padding-inline: var(--moduix-spacing-4);

    &[data-state='open'] {
      color: var(--moduix-color-primary);
    }
  }
}
```

Prefer a direct consumer class whenever the part is available. Put classes or local variables on
portalled parts themselves, or scope them to the portal container.

## Use Panda CSS

Panda CSS can generate consumer classes for every supported framework. Its token names come from your Panda
theme, not from Moduix. Generate class strings once, then attach them to exported parts with
`className` in React or `class` in Solid.

```ts
import { css } from '../styled-system/css';

const trigger = css({
  display: 'grid',
  gridTemplateColumns: 'minmax(0, 1fr) auto',
  px: '4',
  py: '4',
  _hover: { bg: 'blue.100' },
  '&[data-state=open]': { color: 'blue.700' },
});
```

## Use Tailwind CSS

Tailwind packages already contain the component's default utility-backed styling. Add consumer
utilities to the exact part you want to change. The component API remains native to each framework:

## Troubleshoot the cascade

| Symptom | Check |
| --- | --- |
| A variable has no effect | Confirm the component documents it and the override loads after `style.css`. |
| A popup ignores a wrapper-scoped value | Put the value on the portalled part, root, or portal container. |
| A state selector never matches | Inspect the exact Ark state attribute on that part. |
| A class reaches the root but not an inner part | Apply it to the exported part that owns the property. |
| Tailwind utilities are missing | Check the package stylesheet, `@source` path, and consumer class order. |

Inspect the rendered part, `data-slot`, state attributes, and computed values before increasing
specificity.
