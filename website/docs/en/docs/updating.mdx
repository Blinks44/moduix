# Update and migration

moduix offers two ways to install components. The update process depends on where the component
source lives:

| Installation | Where the source lives | Update process |
| --- | --- | --- |
| `@moduix/react` package | In `node_modules` | Update the package and its peer dependencies with your package manager. |
| shadcn registry | In your application repository | Review registry changes, then merge them with your local source. |

If you are moving an existing shadcn application to moduix, see [Migrate from shadcn](/docs/migrate-from-shadcn).

## Update the npm package

Use the package workflow when you want moduix to remain a dependency and receive updates through
your package manager.

Before changing versions, read the [Changelog](/docs/changelog). Use `npm update` for compatible
updates that stay within the version ranges already declared in `package.json`:

The examples below use npm. If you use pnpm, Yarn, or another package manager, use its equivalent
commands.

```bash
npm update @moduix/react @ark-ui/react
```

To choose versions explicitly and update the declared ranges, install the releases you want:

```bash
npm install @moduix/react@latest @ark-ui/react@latest
```

`@ark-ui/react` is a peer dependency of `@moduix/react`. Before a major update, check the
compatible Ark UI range in the release notes instead of upgrading both packages blindly. Choose
the moduix major version deliberately, then follow the migration steps in its changelog.

After the update, review the lockfile, run your application's typecheck and tests, and exercise
the components named in the changelog. If the release changes composition or styling, compare the
component documentation with your implementation before shipping the update.

## Update registry components

Registry components are copied into your application repository. They do not update when you
upgrade `@moduix/react`, so review each registry item separately.

Before changing local files, inspect the current item and compare it with your copy:

```bash
npx shadcn@latest view @moduix-react/button
npx shadcn@latest add @moduix-react/button --dry-run
npx shadcn@latest add @moduix-react/button --diff
```

Replace `button` with the item you want to update. `view` shows the current registry source,
`--dry-run` previews the files that would change, and `--diff` compares the registry version with
the files in your project. A diff can include shared foundation files and other registry
dependencies, so review those changes too.

After reviewing the diff, run the update from a branch or a clean working tree:

```bash
npx shadcn@latest add @moduix-react/button
```

Do not use `--overwrite` until you have decided how to preserve your local edits. If you changed a
component in your application, merge the upstream changes with those edits and then verify the
component's behavior, accessibility, and styles.

Repeat the process for every registry item you use. The CLI resolves the shared moduix foundation
and declared item dependencies automatically. Keep the generated foundation stylesheet imported
once in your application entry point:

```tsx
import '@/lib/moduix/styles/style.css';
```

## Update presets

Presets shipped with `@moduix/react` are updated together with the package. Review [Themes](/docs/themes)
and [Tokens](/docs/tokens) when a release changes density, colors, or other shared visual defaults.

For a preset copied from the registry, inspect and update it like any other registry item:

```bash
npx shadcn@latest view @moduix-react/theme-soft
npx shadcn@latest add @moduix-react/theme-soft --dry-run
npx shadcn@latest add @moduix-react/theme-soft --diff
```

After reviewing the diff, install the preset without `--dry-run` and keep your application
overrides after its import. This preserves the cascade when the preset gains a new token:

```tsx
import '@/lib/moduix/styles/style.css';
import '@/lib/moduix/presets/soft.css';
```
