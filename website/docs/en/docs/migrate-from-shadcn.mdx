# Migrate from shadcn

If your application already uses shadcn, you can move to moduix one component at a time. The two
libraries can coexist while you replace individual screens or component families.

The main choice is where each component's source code should live. Use the npm package when you
want package-managed updates. Use the shadcn-compatible registry when you want the source and styles
in your own repository. Choose React when you are replacing components inside the existing shadcn
application. Choose Solid only when the application itself already uses Solid or the migration also
includes a deliberate framework change.

## Choose where the source code lives

| moduix installation | Choose it when | How updates work |
| --- | --- | --- |
| npm package | You want components to remain a dependency and use imports from `@moduix/react/*` or `@moduix/solid/*`. | Update the package with your package manager. |
| shadcn-compatible registry | You want to version, inspect, and edit component source in your application. | Review and merge each registry update yourself. |

Read the [Quick start](/docs/quick-start) for the complete setup. If your project already has a
shadcn CLI configuration, keep its CLI and `components.json`. Add the moduix registry and aliases
described in the quick start.

## Install moduix beside existing shadcn components

Keep existing shadcn imports and replace them incrementally. For the package workflow, install
moduix and import each component from its subpath:

<Tabs groupId="framework">
  <Tab label="React" value="react">

```tsx
import { Dialog } from '@moduix/react/dialog';
```

  </Tab>
  <Tab label="Solid" value="solid">

```tsx
import { Dialog } from '@moduix/solid/dialog';
```

  </Tab>
</Tabs>

For the copy-owned workflow, finish the [shadcn CLI setup](/docs/quick-start#install-with-the-shadcn-cli),
then add one registry item at a time:

<Tabs groupId="framework">
  <Tab label="React" value="react">

<PackageManagerTabs command="shadcn@latest add @moduix-react/dialog" dlx />

  </Tab>
  <Tab label="Solid" value="solid">

<PackageManagerTabs command="shadcn@latest add @moduix-solid/dialog" dlx />

  </Tab>
</Tabs>

The CLI writes the component source and its moduix dependencies to the aliases in `components.json`.
Import the generated component from your application:

```tsx
import { Dialog } from '@/components/ui/dialog';
```

## Find the closest component

moduix usually names a component after the interaction it provides. The table below maps common
shadcn names to the corresponding moduix component and calls out the changes that matter during a
migration.

| Familiar shadcn name | Use in moduix | What to change |
| --- | --- | --- |
| Accordion | `Accordion` | Import flat parts such as `AccordionItem` and `AccordionItemContent`. |
| Alert Dialog | `Dialog` | Set `role="alertdialog"` on `DialogContent` for a critical confirmation flow. |
| Avatar | `Avatar` | Put fallback content and the image in `AvatarFallback` and `AvatarImage`. |
| Breadcrumb | `Breadcrumbs` | The family name is plural; keep semantic links and the current-page state. |
| Calendar | `DatePicker` or `DateInput` | Use `DatePicker` for a calendar and `DateInput` when users only need editable date segments. |
| Carousel | `Carousel` | Compose the controls, indicators, and item group from its named parts. |
| Collapsible | `Collapsible` | Read `details.open` from `onOpenChange(details)` instead of accepting a boolean. |
| Combobox | `Combobox` | Create an Ark collection and define item values for object-based items. |
| Command | `CommandPalette` | Use the command-oriented component instead of a generic list alias. |
| Context Menu | `MenuContextTrigger` | Keep the same `Menu` family and use its context trigger. |
| Data Table | `Table` plus the Data Table recipe | Keep sorting, filtering, and server state in application code. |
| Date Picker | `DatePicker` | Use the composed date input and calendar family. |
| Dropdown Menu | `Menu` | Use the regular `MenuTrigger` composition. |
| Form | `Field` and `Fieldset` | Use them for field structure; keep validation and submission in your form library or application. |
| Hover Card | `HoverCard` | Check the target page for the explicit positioning and lifecycle parts. |
| Input OTP | `PinInput` | Preserve its native form and SSR setup. |
| Progress | `ProgressLinear` or `ProgressCircular` | Choose the visual form explicitly. |
| Resizable | `Splitter` | Give panels stable ids and keep layout state explicit. |
| Select | `Select` | Use an Ark collection instead of an ad hoc array of option objects. |
| Sheet | `Drawer` | Use the edge-panel component with a Dialog-aligned lifecycle. |
| Sidebar | `Sidebar` | Keep your product navigation and responsive composition in the application. |
| Sonner / Toast | `Toast` and `Toaster` | Keep notification text and when to show it under application control. |
| Tabs | `Tabs` | Use flat parts such as `TabsList` and `TabsTrigger` for the same interaction. |
| Toggle Group | `ToggleGroup` | Use item values and group state from the Ark contract. |
| Tooltip | `Tooltip` | Keep the trigger and portalled content explicit. |

Navigation Menu and Menubar do not need forced one-to-one replacements. Choose `Sidebar`, `Menu`,
`Breadcrumbs`, or ordinary links based on the interaction your product needs.

## Adapt the import shape

shadcn commonly exports each part as a separate local symbol:

```tsx
import { Dialog, DialogContent, DialogTitle, DialogTrigger } from '@/components/ui/dialog';
```

moduix uses the same flat family-prefixed shape across frameworks:

<Tabs groupId="framework">
  <Tab label="React" value="react">

```tsx
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/react/accordion';

export function FrequentlyAskedQuestions() {
  return (
    <Accordion defaultValue={['first']}>
      <AccordionItem value="first">
        <AccordionItemTrigger>What is moduix?</AccordionItemTrigger>
        <AccordionItemContent>A multi-framework component system.</AccordionItemContent>
      </AccordionItem>
    </Accordion>
  );
}
```

  </Tab>
  <Tab label="Solid" value="solid">

```tsx
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/solid/accordion';

export function FrequentlyAskedQuestions() {
  return (
    <Accordion defaultValue={['first']}>
      <AccordionItem value="first">
        <AccordionItemTrigger>What is moduix?</AccordionItemTrigger>
        <AccordionItemContent>A multi-framework component system.</AccordionItemContent>
      </AccordionItem>
    </Accordion>
  );
}
```

  </Tab>
</Tabs>

For a copy-owned install, keep the composition and change only the import source:

```tsx
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@/components/ui/accordion';
```

The family name is the root. Every additional value is a direct family-prefixed export, with no
namespace object or dotted part access.

## Keep your existing styling workflow

moduix provides finished component styles and shared `--moduix-*` tokens. Import the foundation
stylesheet once, then put your application overrides in a stylesheet loaded after it.

With a CSS Modules npm package:

<Tabs groupId="framework">
  <Tab label="React" value="react">

```tsx
import '@moduix/react/style.css';
```

  </Tab>
  <Tab label="Solid" value="solid">

```tsx
import '@moduix/solid/style.css';
```

  </Tab>
</Tabs>

With a CSS Modules registry:

```tsx
import '@/lib/moduix/styles/style.css';
```

Customize semantic tokens in your own CSS:

```css title="app.css"
:root {
  --moduix-color-accent: oklch(58% 0.18 260deg);
  --moduix-radius-md: 0.625rem;
}
```

Tailwind can stay in the application for layout and one-off utility classes while you migrate to the
CSS Modules packages. If you want component styling to remain in Tailwind, use the separate React or
Solid Tailwind package where that component is available. Use the target component page for stable
slots, CSS variables, and React `className` or Solid `class` props.

## Adapt Ark state callbacks and collections

Ark callbacks receive a `details` object. Read the value you need from that object instead of
copying a shadcn callback that expects a positional value:

<Tabs groupId="framework">
  <Tab label="React" value="react">

```tsx
import { useState } from 'react';
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/react/accordion';

export function ControlledAccordion() {
  const [value, setValue] = useState<string[]>([]);

  return (
    <Accordion value={value} onValueChange={(details) => setValue(details.value)}>
      <AccordionItem value="first">
        <AccordionItemTrigger>What is moduix?</AccordionItemTrigger>
        <AccordionItemContent>A multi-framework component system.</AccordionItemContent>
      </AccordionItem>
    </Accordion>
  );
}
```

  </Tab>
  <Tab label="Solid" value="solid">

```tsx
import { createSignal } from 'solid-js';
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/solid/accordion';

export function ControlledAccordion() {
  const [value, setValue] = createSignal<string[]>([]);

  return (
    <Accordion value={value()} onValueChange={(details) => setValue(details.value)}>
      <AccordionItem value="first">
        <AccordionItemTrigger>What is moduix?</AccordionItemTrigger>
        <AccordionItemContent>A multi-framework component system.</AccordionItemContent>
      </AccordionItem>
    </Accordion>
  );
}
```

  </Tab>
</Tabs>

Components with collections, including `Combobox` and `Select`, use explicit Ark collection state.
For object items, define how an item becomes its visible string and stable value with
`itemToString` and `itemToValue`. Check the target component page before copying a shadcn
`options` array or callback unchanged.

## Migrate one slice at a time

1. Add the moduix foundation stylesheet and keep it before your application overrides.
2. Start with low-dependency components such as `Button`, `Badge`, `Avatar`, and `Separator`.
3. Move overlays and collection components one family at a time, including their portal parts and state callbacks.
4. Use a [recipe](/recipes) only when its screen-level flow matches your product.
5. Verify keyboard behavior, focus restoration, labels, and critical roles, then remove the old component source and styles.

Keep application responsibilities in the application. Labels, validation messages, permissions,
server calls, and product flows do not belong in a generic component wrapper. Ark provides primitive
behavior, while moduix provides the component API, styles, and defaults.

Use [Updating and migration](/docs/updating) for later package or registry upgrades. Read
[Composition Patterns](/docs/composition-patterns) when adapting existing wrappers.
