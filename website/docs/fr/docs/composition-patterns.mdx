# Modèles de composition

moduix ne masque pas la composition d’Ark. Au lieu d’un grand ensemble de props, la plupart des composants exposent
une racine avec état et des parties distinctes pour la sémantique, la mise en page et le style.

Vous disposez ainsi d’une progression claire pour personnaliser les composants :

- utilisez directement les parties fournies ;
- réexportez-les sous des noms propres à votre produit ;
- n’enveloppez que les parties qui exigent des styles ou une mise en page récurrents.

Ces principes restent les mêmes avec `@moduix/react` comme avec le code source installé depuis le registre.

## Choisir une installation

Choisissez le package npm pour recevoir les mises à jour via votre gestionnaire de paquets, importer les
composants depuis `@moduix/react/*` et des styles depuis `@moduix/react/style.css`.

Choisissez le registre `shadcn` si vous voulez conserver le code source des composants dans l’application. Il ajoute
à votre projet le composant choisi, ainsi que les styles, icônes et utilitaires moduix nécessaires. Vous pouvez
ensuite les modifier directement et les importer depuis `@/components/moduix/*`.

Les composants dont vous conservez le code source ne reçoivent pas automatiquement les mises à jour du package.
Lorsqu’une nouvelle version de moduix est disponible, ajoutez-la avec `shadcn`, puis examinez et fusionnez le diff.
La configuration initiale du registre et les commandes des composants sont décrites dans le
[Démarrage rapide](/docs/quick-start#install-with-the-shadcn-cli).

## Arborescence des parties

Avant de créer des wrappers, partez de l’arborescence présentée sur la page du composant. Appliquez `className`, les
variables CSS, `data-slot` et les attributs d’état Ark aux parties auxquelles ces responsabilités appartiennent.

Les exports racines comme `Popover`, `Tooltip` et `Select` sont des formes courtes de `*.Root`. Les racines des
composants flottants ou de type dialogue placent automatiquement leur sous-arbre d’overlay dans un portail. La
structure reste donc visible, sans wrapper `Portal` distinct.

Par exemple :

```text
Dialog / Dialog.Root
├─ Dialog.Trigger
├─ Overlay subtree (automatically portalled)
│  ├─ Dialog.Backdrop
│  └─ Dialog.Positioner
│     └─ Dialog.Content
│        ├─ Dialog.Title
│        ├─ Dialog.Description
│        └─ Dialog.CloseTrigger
```

Utilisez `portalled={false}` pour un rendu dans le flux et `portalRef` pour un conteneur personnalisé lorsque
le composant prend en charge ces props. Utilisez `Dialog.RootProvider` comme point d’entrée alternatif pour
l’état lorsque l’objet d’état se trouve hors du sous-arbre rendu.

## Parties structurelles

Toutes les primitives n’exposent pas chacune des parties ci-dessous. Appuyez-vous sur l’anatomie de la page du
composant et gardez visibles les parties que votre produit pourra devoir redéfinir.

| Partie | Responsabilité |
| --- | --- |
| `Backdrop` | Assure la séparation modale et sert de cible aux interactions extérieures. |
| `Positioner` | Gère le placement dans la fenêtre ou par rapport à une ancre, ainsi que le défilement. |
| `Content` | Rend la surface interactive et reçoit les attributs d’état. |
| `Arrow` | Relie le contenu flottant ancré à son déclencheur lorsque la primitive prend cette partie en charge. |

Ne masquez pas ces nœuds dans des wrappers du produit, sauf si le contrat du produit supprime
intentionnellement leurs points de personnalisation.

## `asChild`

Utilisez `asChild` lorsqu’un élément sémantique existant doit posséder le nœud DOM, tandis qu’une partie moduix y
attache son comportement.

```tsx
import { Button } from '@moduix/react/button';
import { Popover } from '@moduix/react/popover';
// shadcn copy-owned: import { Button } from '@/components/moduix/button';
// shadcn copy-owned: import { Popover } from '@/components/moduix/popover';

export function FiltersPopover() {
  return (
    <Popover positioning={{ gutter: 8 }}>
      <Popover.Trigger asChild>
        <Button variant="outline">Filters</Button>
      </Popover.Trigger>
      <Popover.Positioner>
        <Popover.Content>Choose one or more filters.</Popover.Content>
      </Popover.Positioner>
    </Popover>
  );
}
```

Conservez un seul enfant sémantique capable de recevoir les props Ark. Si le composant enfant ne transmet pas la ref,
les gestionnaires d’événements ou les attributs, `asChild` ne fonctionnera pas correctement.

## `ids`

La plupart des relations sont créées automatiquement. Transmettez `ids` seulement lorsque deux primitives doivent
pointer vers le même déclencheur ou le même nœud de description, plutôt que d’écrire les relations ARIA à la main.

```tsx
import { Avatar } from '@moduix/react/avatar';
import { Tooltip } from '@moduix/react/tooltip';
import { useId } from 'react';

export function AssigneeTooltip() {
  const id = useId();

  return (
    <Tooltip ids={{ trigger: id }}>
      <Tooltip.Trigger asChild>
        <Avatar ids={{ root: id }}>
          <Avatar.Fallback name="Sam Ortiz" />
        </Avatar>
      </Tooltip.Trigger>
      <Tooltip.Body>Sam Ortiz is online</Tooltip.Body>
    </Tooltip>
  );
}
```

Ark reste ainsi responsable des relations d’accessibilité, sans dupliquer manuellement les attributs `aria-*`.

## Réexporter d’abord

Si votre produit a besoin d’imports plus courts ou de sa propre API, commencez par des réexports plutôt que par de
nouvelles abstractions. Ils préservent le comportement d’origine tout en donnant à l’application une API locale stable.

```tsx
import { Dialog as ModuixDialog } from '@moduix/react/dialog';
// shadcn copy-owned: import { Dialog as ModuixDialog } from '@/components/moduix/dialog';

export const Dialog = ModuixDialog;
export const DialogTrigger = ModuixDialog.Trigger;
export const DialogBackdrop = ModuixDialog.Backdrop;
export const DialogPositioner = ModuixDialog.Positioner;
export const DialogContent = ModuixDialog.Content;
export const DialogTitle = ModuixDialog.Title;
export const DialogDescription = ModuixDialog.Description;
export const DialogCloseTrigger = ModuixDialog.CloseTrigger;
```

C’est la voie de personnalisation la moins risquée :

- les consommateurs importent depuis la couche du produit, et non directement depuis `@moduix/react/*`
  ou `@/components/moduix/*` ;
- le comportement Ark reste intact ;
- le passage du package à une installation possédée en code source reste simple ;
- des wrappers peuvent être ajoutés plus tard uniquement là où ils sont réellement nécessaires.

## Contrat produit

Donnez le contrat produit uniquement à la partie qui porte cette décision. Le `Dialog` local forme une frontière
produit complète : les consommateurs importent un seul composant et utilisent `Dialog.Trigger`, `Dialog.Content` et
toutes les autres parties depuis celui-ci. En interne, seule la surface du dialogue ajoute le petit contrat `tone`,
car elle porte cette décision visuelle.

Les consommateurs importent alors uniquement le composant produit :

```tsx
import { Dialog } from '@/components/ui/dialog';

export function DeleteProjectDialog() {
  return (
    <Dialog>
      <Dialog.Trigger>Delete project</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content tone="danger">
          <Dialog.Header>
            <Dialog.Title>Delete this project?</Dialog.Title>
            <Dialog.CloseIcon />
            <Dialog.Description>This cannot be undone.</Dialog.Description>
          </Dialog.Header>
          <Dialog.Footer>
            <Dialog.CloseTrigger>Cancel</Dialog.CloseTrigger>
          </Dialog.Footer>
        </Dialog.Content>
      </Dialog.Positioner>
    </Dialog>
  );
}
```

La racine produit conserve l’API moduix complète. Son `Dialog.Content` personnalisé transmet la ref,
`className` et toutes les props existantes du contenu. L’attribut `data-dialog-tone` sert de crochet de
style produit ; le CSS le relie aux variables publiques du dialogue, sans recopier les styles du composant.

Gardez l’arborescence des parties explicite : `Dialog.Backdrop`, `Dialog.Positioner` et
`Dialog.Content` indiquent toujours clairement où vivent le comportement de l’overlay et le style.
N’ajoutez un wrapper que lorsqu’il représente une décision produit répétée, et non pour une classe ponctuelle.

## État externe

Ne sortez l’état de l’arborescence que lorsque sa propriété change, et conservez les objets de détail Ark tels quels.
Par exemple, l’état d’ouverture d’une boîte de dialogue continue d’utiliser `onOpenChange(details)` et de lire
`details.open`.

Utilisez les helpers d’état du composant seulement lorsque l’état doit vivre hors du sous-arbre rendu :

- `Component.Context` pour une lecture ponctuelle dans le JSX ;
- `useComponentContext()` dans les descendants déjà placés sous la partie racine ;
- `useComponent()` avec `Component.RootProvider` lorsque l’état est créé hors de l’arborescence rendue.

```tsx
import { Dialog, useDialog } from '@moduix/react/dialog';

export function DialogFromExternalState() {
  const dialog = useDialog();

  return (
    <Dialog.RootProvider value={dialog}>
      <Dialog.Trigger>Open dialog</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content>State is owned by useDialog().</Dialog.Content>
      </Dialog.Positioner>
    </Dialog.RootProvider>
  );
}
```

Ne rendez pas `Root` et `RootProvider` pour une même instance d’état.

## Choisir un niveau

- Vous avez seulement besoin de l’usage prévu ? Restez sur les parties fournies.
- Vous avez besoin de chemins d’import propres au produit ? Commencez par réexporter.
- Vous avez besoin d’un système visuel récurrent pour le produit ? Enveloppez les parties précises qui en
  sont responsables.
- Vous avez besoin d’un comportement différent ? Utilisez une arborescence explicite de parties au lieu
  d’inventer de nouvelles props de haut niveau.
