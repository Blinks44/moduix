# Modèles de composition

`moduix` laisse visible le modèle de composition d’Ark. La plupart des composants exposent une racine qui gère l’état
et des parties distinctes pour la structure, la sémantique et les styles. Vous savez ainsi quelle couche porte chaque
responsabilité et disposez d’une manière prévisible de personnaliser un composant :

- utilisez directement les parties fournies ;
- réexportez-les depuis la couche de votre produit ;
- n’enveloppez que les parties qui ont besoin de styles ou d’une mise en page récurrents pour le produit.

La même approche fonctionne avec `@moduix/react` et avec le code source copié depuis le registre.

## Choisir une installation

Choisissez le package npm si vous voulez laisser votre gestionnaire de paquets gérer les mises à jour. Importez les
composants depuis `@moduix/react/*` et les styles partagés depuis `@moduix/react/style.css`.

Choisissez le registre `shadcn` si votre application doit posséder le code source des composants. Il copie le
composant choisi ainsi que les styles, icônes et utilitaires moduix dont il dépend dans votre projet. Vous pouvez
ensuite modifier ce code directement et importer les composants depuis `@/components/moduix/*`.

Les composants dont le code source vit dans votre application ne reçoivent pas automatiquement les mises à jour du
package. Lorsqu’une nouvelle version de moduix est disponible, ajoutez de nouveau le composant avec `shadcn`, puis
examinez et fusionnez le diff obtenu. Consultez le [Démarrage rapide](/docs/quick-start#installer-avec-la-cli-shadcn)
pour la configuration initiale du registre et les commandes d’ajout des composants.

## Utiliser l’arborescence des parties

Avant de créer des wrappers, commencez par l’arborescence présentée sur la page du composant. Appliquez `className`,
les variables CSS, `data-slot` et les attributs d’état Ark aux parties qui portent réellement ces responsabilités.

Les exports racine comme `Popover`, `Tooltip` et `Select` sont des raccourcis de `*.Root`. Pour les composants de
type boîte de dialogue et les composants flottants, la racine place automatiquement le sous-arbre d’overlay dans un
portail. La structure reste donc explicite sans wrapper `Portal` distinct.

Par exemple :

```text
Dialog / Dialog.Root
├─ Dialog.Trigger
├─ Sous-arbre de l’overlay (rendu automatiquement dans un portail)
│  ├─ Dialog.Backdrop
│  └─ Dialog.Positioner
│     └─ Dialog.Content
│        ├─ Dialog.Title
│        ├─ Dialog.Description
│        └─ Dialog.CloseTrigger
```

Utilisez `portalled={false}` pour un rendu à l’emplacement du composant et `portalRef` pour votre propre conteneur
lorsque le composant prend ces props en charge. Utilisez `Dialog.RootProvider` lorsque l’objet d’état est créé en
dehors de l’arborescence rendue.

## Parties structurelles

Toutes les primitives n’exposent pas chacune des parties ci-dessous. Commencez par l’anatomie de la page du composant,
puis gardez visibles les parties que votre produit pourra devoir personnaliser.

| Partie        | Responsabilité                                                                   |
| ------------- | ------------------------------------------------------------------------------- |
| `Backdrop`    | Sépare une surface modale du reste de la page et reçoit les interactions extérieures. |
| `Positioner`  | Gère le placement dans la fenêtre ou par rapport à une ancre, ainsi que le défilement. |
| `Content`     | Rend la surface interactive et reçoit les attributs d’état.                     |
| `Arrow`       | Relie le contenu flottant ancré à son déclencheur lorsque la primitive prend cette partie en charge. |

Ne masquez pas ces nœuds dans des wrappers du produit, sauf si le contrat du produit supprime intentionnellement
leurs points de personnalisation.

## `asChild`

Utilisez `asChild` lorsqu’un élément sémantique existant doit être rendu comme nœud DOM et qu’une partie moduix doit
simplement lui ajouter son comportement.

```tsx
import { Button } from '@moduix/react/button';
import { Popover } from '@moduix/react/popover';
// shadcn copy-owned: import { Button } from '@/components/moduix/button';
// shadcn copy-owned: import { Popover } from '@/components/moduix/popover';

export function FiltersPopover() {
  return (
    <Popover positioning={{ gutter: 8 }}>
      <Popover.Trigger asChild>
        <Button variant="outline">Filters</Button>
      </Popover.Trigger>
      <Popover.Positioner>
        <Popover.Content>Choose one or more filters.</Popover.Content>
      </Popover.Positioner>
    </Popover>
  );
}
```

Gardez un seul enfant sémantique capable de recevoir les props Ark. Si le composant enfant ne transmet pas la ref,
les gestionnaires d’événements ou les attributs, `asChild` ne fonctionnera pas correctement.

## `ids`

Dans la plupart des compositions, les relations sont créées automatiquement. Utilisez `ids` lorsque deux primitives
doivent coordonner un identifiant stable, par exemple lorsqu’elles partagent le même élément déclencheur. N’écrivez
pas les relations ARIA à la main.

```tsx
import { Avatar } from '@moduix/react/avatar';
import { Tooltip } from '@moduix/react/tooltip';
import { useId } from 'react';

export function AssigneeTooltip() {
  const id = useId();

  return (
    <Tooltip ids={{ trigger: id }}>
      <Tooltip.Trigger asChild>
        <Avatar ids={{ root: id }}>
          <Avatar.Fallback name="Sam Ortiz" />
        </Avatar>
      </Tooltip.Trigger>
      <Tooltip.Body>Sam Ortiz is online</Tooltip.Body>
    </Tooltip>
  );
}
```

Ark reste ainsi responsable des relations d’accessibilité, sans que vous ayez à dupliquer manuellement les attributs
`aria-*`.

## Réexporter d’abord

Si votre produit a besoin de chemins d’import plus courts ou de sa propre API, commencez par des réexportations plutôt
que par de nouvelles abstractions. Elles préservent le comportement d’origine tout en donnant à l’application une
API locale stable.

```tsx
import { Dialog as ModuixDialog } from '@moduix/react/dialog';
// shadcn copy-owned: import { Dialog as ModuixDialog } from '@/components/moduix/dialog';

export const Dialog = ModuixDialog;
export const DialogTrigger = ModuixDialog.Trigger;
export const DialogBackdrop = ModuixDialog.Backdrop;
export const DialogPositioner = ModuixDialog.Positioner;
export const DialogContent = ModuixDialog.Content;
export const DialogTitle = ModuixDialog.Title;
export const DialogDescription = ModuixDialog.Description;
export const DialogCloseTrigger = ModuixDialog.CloseTrigger;
```

C’est l’option de personnalisation la moins risquée :

- les consommateurs importent depuis la couche du produit, et non directement depuis `@moduix/react/*` ou `@/components/moduix/*` ;
- le comportement Ark reste inchangé ;
- le passage du package à une version dont le code source appartient à l’application reste simple ;
- des wrappers peuvent être ajoutés plus tard uniquement là où ils sont réellement nécessaires.

## Ajouter un contrat produit

Donnez un contrat produit uniquement à la partie qui porte la décision correspondante. Le `Dialog` local devient une
frontière complète du produit : les consommateurs importent un seul composant, puis utilisent `Dialog.Trigger`,
`Dialog.Content` et les autres parties depuis celui-ci. En interne, seule la surface du dialogue ajoute le petit
contrat `tone`, car c’est elle qui porte la décision visuelle.

Les consommateurs importent alors uniquement le composant du produit :

```tsx
import { Dialog } from '@/components/ui/dialog';

export function DeleteProjectDialog() {
  return (
    <Dialog>
      <Dialog.Trigger>Delete project</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content tone="danger">
          <Dialog.Header>
            <Dialog.Title>Delete this project?</Dialog.Title>
            <Dialog.CloseIcon />
            <Dialog.Description>This cannot be undone.</Dialog.Description>
          </Dialog.Header>
          <Dialog.Footer>
            <Dialog.CloseTrigger>Cancel</Dialog.CloseTrigger>
          </Dialog.Footer>
        </Dialog.Content>
      </Dialog.Positioner>
    </Dialog>
  );
}
```

La racine du produit conserve l’API moduix complète. Son `Dialog.Content` personnalisé transmet la `ref`,
`className` et toutes les props existantes du contenu. L’attribut `data-dialog-tone` sert de crochet de style du
produit ; le CSS le relie aux variables publiques du dialogue, sans recopier les styles du composant.

Gardez l’arborescence des parties explicite : `Dialog.Backdrop`, `Dialog.Positioner` et `Dialog.Content` indiquent
clairement où se trouvent le comportement de l’overlay et la responsabilité des styles. N’ajoutez un wrapper que
lorsqu’il représente une décision récurrente du produit, et non pour une classe ponctuelle.

## État hors de l’arborescence

Déplacez l’état hors de l’arborescence uniquement lorsque sa propriété change, et conservez les objets de détail Ark
intacts. Par exemple, l’état d’ouverture du dialogue utilise toujours `onOpenChange(details)` et lit `details.open`.

Utilisez les API d’état du composant selon l’endroit où vous devez y accéder :

- `Dialog.Context` pour une lecture ponctuelle dans l’arbre de rendu ;
- `useDialogContext()` dans des descendants réutilisables déjà placés sous la racine ;
- `useDialog()` avec `Dialog.RootProvider` lorsque l’état est créé en dehors de l’arborescence rendue.

```tsx
import { Dialog, useDialog } from '@moduix/react/dialog';

export function DialogFromExternalState() {
  const dialog = useDialog();

  return (
    <Dialog.RootProvider value={dialog}>
      <Dialog.Trigger>Open dialog</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content>State is owned by useDialog().</Dialog.Content>
      </Dialog.Positioner>
    </Dialog.RootProvider>
  );
}
```

Ne rendez pas `Root` et `RootProvider` pour une même instance d’état.

## Choisir un niveau

- Vous avez seulement besoin de l’usage standard ? Restez sur les parties fournies.
- Vous avez besoin de chemins d’import propres au produit ? Commencez par réexporter.
- Vous avez besoin de visuels récurrents pour le produit ? Enveloppez les parties précises qui en sont responsables.
- Vous avez besoin d’un comportement différent ? Utilisez l’arborescence explicite des parties au lieu d’inventer de nouvelles props de haut niveau.
