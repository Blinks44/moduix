# Migrer depuis shadcn vers moduix

Si votre application utilise déjà shadcn, vous pouvez passer à moduix composant par composant. Les
deux bibliothèques peuvent cohabiter pendant que vous remplacez certains écrans ou certaines
familles de composants.

Le choix principal concerne l’emplacement du code source. Utilisez le paquet npm si vous voulez
recevoir les mises à jour par votre gestionnaire de paquets. Utilisez le registre compatible avec
shadcn si vous voulez conserver le code source et les styles dans votre dépôt.
Choisissez React pour remplacer des composants dans une application shadcn existante. Choisissez
Solid uniquement si l’application utilise déjà Solid ou si la migration comprend aussi un changement
de framework volontaire.

## Choisissez où conserver le code source

| Installation moduix | À privilégier si | Fonctionnement des mises à jour |
| --- | --- | --- |
| Paquet npm | Vous voulez que les composants restent une dépendance et utiliser des imports depuis `@moduix/react/*` ou `@moduix/solid/*`. | Mettez le paquet à jour avec votre gestionnaire de paquets. |
| Registre compatible avec shadcn | Vous voulez versionner, consulter et modifier le code source des composants dans votre application. | Examinez et fusionnez vous-même chaque mise à jour du registre. |

Consultez le [Démarrage rapide](/docs/quick-start) pour la configuration complète. Si votre projet
possède déjà une configuration du CLI shadcn, gardez son CLI et `components.json`. Ajoutez le
registre moduix et les alias indiqués dans le guide.

## Installez moduix à côté des composants shadcn existants

Conservez les imports shadcn déjà en place et remplacez les composants progressivement. Avec le
paquet npm, importez chaque composant depuis son sous-chemin :

<Tabs groupId="framework">
  <Tab label="React" value="react">

```tsx
import { Dialog } from '@moduix/react/dialog';
```

  </Tab>
  <Tab label="Solid" value="solid">

```tsx
import { Dialog } from '@moduix/solid/dialog';
```

  </Tab>
</Tabs>

Avec le code copié dans votre projet, terminez la [configuration du CLI shadcn](/docs/quick-start#installer-avec-la-cli-shadcn),
puis ajoutez les éléments du registre un par un :

<Tabs groupId="framework">
  <Tab label="React" value="react">

<PackageManagerTabs command="shadcn@latest add @moduix-react/dialog" dlx />

  </Tab>
  <Tab label="Solid" value="solid">

<PackageManagerTabs command="shadcn@latest add @moduix-solid/dialog" dlx />

  </Tab>
</Tabs>

Le CLI écrit le code source du composant et les dépendances moduix nécessaires dans les chemins
définis par `components.json`. Importez ensuite le composant généré depuis votre application :

```tsx
import { Dialog } from '@/components/ui/dialog';
```

## Trouvez le composant le plus proche

moduix nomme généralement ses composants d’après l’interaction qu’ils proposent. Le tableau ci-dessous
met en regard les noms shadcn courants et leurs équivalents moduix, avec les adaptations importantes
pour la migration.

| Nom shadcn habituel | Utilisez dans moduix | Adaptation à prévoir |
| --- | --- | --- |
| Accordion | [`Accordion`](/docs/accordion) | Utilisez les parties nommées, comme `AccordionItem` et `AccordionItemContent`. |
| Alert Dialog | [`Dialog`](/docs/dialog) | Pour une confirmation critique, définissez `role="alertdialog"` sur `DialogContent`. |
| Avatar | [`Avatar`](/docs/avatar) | Placez le contenu de repli et l’image dans `AvatarFallback` et `AvatarImage`. |
| Breadcrumb | [`Breadcrumbs`](/docs/breadcrumbs) | Le nom de la famille est au pluriel ; conservez les liens sémantiques et l’état de la page courante. |
| Calendar | [`DatePicker`](/docs/date-picker) ou [`DateInput`](/docs/date-input) | Utilisez `DatePicker` pour un calendrier et `DateInput` si seule la saisie de segments de date est nécessaire. |
| Carousel | [`Carousel`](/docs/carousel) | Composez les contrôles, les indicateurs et le groupe d’éléments avec les parties nommées. |
| Collapsible | [`Collapsible`](/docs/collapsible) | Lisez `details.open` dans `onOpenChange(details)` au lieu d’attendre un booléen. |
| Combobox | [`Combobox`](/docs/combobox) | Créez une collection Ark et définissez les valeurs des éléments-objets. |
| Command | [`CommandPalette`](/docs/command-palette) | Utilisez le composant dédié aux commandes plutôt qu’un alias de liste générique. |
| Context Menu | [`MenuContextTrigger`](/docs/menu) | Conservez la famille `Menu` et utilisez son déclencheur contextuel. |
| Data Table | [`Table`](/docs/table) et la [recette Data Table](/recipes/data-table) | Gardez le tri, le filtrage et l’état serveur dans le code de l’application. |
| Date Picker | [`DatePicker`](/docs/date-picker) | Utilisez la famille composée qui réunit saisie de date et calendrier. |
| Dropdown Menu | [`Menu`](/docs/menu) | Utilisez la composition habituelle avec `MenuTrigger`. |
| Form | [`Field`](/docs/field) et [`Fieldset`](/docs/fieldset) | Utilisez-les pour structurer les champs ; laissez la validation et la soumission à votre bibliothèque de formulaires ou à l’application. |
| Hover Card | [`HoverCard`](/docs/hover-card) | Consultez la page du composant pour les parties explicites de positionnement et de fermeture. |
| Input OTP | [`PinInput`](/docs/pin-input) | Conservez sa configuration pour les formulaires natifs et le SSR. |
| Progress | [`ProgressLinear`](/docs/progress-linear) ou [`ProgressCircular`](/docs/progress-circular) | Choisissez explicitement la forme visuelle souhaitée. |
| Resizable | [`Splitter`](/docs/splitter) | Donnez des identifiants stables aux panneaux et gardez l’état de mise en page explicite. |
| Select | [`Select`](/docs/select) | Utilisez une collection Ark plutôt qu’un tableau d’objets option ad hoc. |
| Sheet | [`Drawer`](/docs/drawer) | Utilisez le composant de panneau latéral dont le cycle de vie est aligné sur celui de Dialog. |
| Sidebar | [`Sidebar`](/docs/sidebar) | Gardez la composition de la navigation produit et son comportement adaptatif dans l’application. |
| Sonner / Toast | [`Toast`](/docs/toast) et [`Toaster`](/docs/toast) | L’application doit garder le contrôle du texte des notifications et du moment où elles apparaissent. |
| Tabs | [`Tabs`](/docs/tabs) | Utilisez les parties plates `TabsList` et `TabsTrigger` pour la même interaction. |
| Toggle Group | [`ToggleGroup`](/docs/toggle-group) | Utilisez les valeurs des éléments et l’état du groupe définis par le contrat Ark. |
| Tooltip | [`Tooltip`](/docs/tooltip) | Gardez explicites le déclencheur et le contenu rendu dans un portail. |

Navigation Menu et Menubar ne nécessitent pas de remplacement forcé un pour un. Choisissez `Sidebar`,
`Menu`, `Breadcrumbs` ou des liens ordinaires selon l’interaction attendue par votre produit.

## Adaptez la forme des imports

Dans shadcn, chaque partie est généralement exportée comme un symbole local distinct :

```tsx
import { Dialog, DialogContent, DialogTitle, DialogTrigger } from '@/components/ui/dialog';
```

moduix utilise les mêmes exports plats préfixés par le nom de la famille dans chaque framework :

```tsx
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/react/accordion';

export function FrequentlyAskedQuestions() {
  return (
    <Accordion defaultValue={['first']}>
      <AccordionItem value="first">
        <AccordionItemTrigger>What is moduix?</AccordionItemTrigger>
        <AccordionItemContent>A multi-framework component system.</AccordionItemContent>
      </AccordionItem>
    </Accordion>
  );
}
```

Avec Solid, seul le spécificateur d’import change :

```tsx
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/solid/accordion';
```

Avec une installation qui copie le code dans le projet, gardez la composition et changez seulement
le chemin d’import :

```tsx
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@/components/ui/accordion';
```

Le nom de la famille désigne la racine. Chaque valeur supplémentaire est exportée directement avec
le préfixe de la famille, sans objet d’espace de noms ni accès par notation pointée.

## Conservez votre approche actuelle des styles

moduix fournit les styles des composants et des tokens partagés `--moduix-*`. Importez une seule fois
la feuille de style de base, puis placez vos surcharges dans une feuille chargée après celle-ci.

Avec un paquet npm fondé sur CSS Modules :

<Tabs groupId="framework">
  <Tab label="React" value="react">

```tsx
import '@moduix/react/style.css';
```

  </Tab>
  <Tab label="Solid" value="solid">

```tsx
import '@moduix/solid/style.css';
```

  </Tab>
</Tabs>

Avec un registre fondé sur CSS Modules :

```tsx
import '@/lib/moduix/styles/style.css';
```

Personnalisez les tokens sémantiques dans votre propre CSS :

```css title="app.css"
:root {
  --moduix-color-accent: oklch(58% 0.18 260deg);
  --moduix-radius-md: 0.625rem;
}
```

Tailwind peut rester dans l’application pour la mise en page et les classes ponctuelles pendant une
migration vers les paquets CSS Modules. Si les styles des composants doivent rester en Tailwind,
utilisez le paquet Tailwind React ou Solid lorsque le composant y est disponible. Consultez sa page
pour connaître ses slots stables, ses variables CSS et ses propriétés `className` ou `class`.

## Adaptez les callbacks Ark et les collections

Les callbacks Ark reçoivent un objet `details`. Lisez-y la valeur nécessaire au lieu de reprendre
tel quel un callback shadcn qui attend un argument positionnel :

```tsx
import { useState } from 'react';
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/react/accordion';

export function ControlledAccordion() {
  const [value, setValue] = useState<string[]>([]);

  return (
    <Accordion value={value} onValueChange={(details) => setValue(details.value)}>
      <AccordionItem value="first">
        <AccordionItemTrigger>What is moduix?</AccordionItemTrigger>
        <AccordionItemContent>A multi-framework component system.</AccordionItemContent>
      </AccordionItem>
    </Accordion>
  );
}
```

Avec Solid, `useState` devient `createSignal` de `solid-js`, le signal se lit avec `value()` et les
imports changent en conséquence :

```tsx
import { createSignal } from 'solid-js';
import { Accordion, AccordionItem, AccordionItemContent, AccordionItemTrigger } from '@moduix/solid/accordion';
```

Les composants qui utilisent des collections, notamment `Combobox` et `Select`, s’appuient sur un
état de collection Ark explicite. Pour des éléments-objets, définissez avec `itemToString` et
`itemToValue` le texte affiché et la valeur stable de chaque élément. Consultez la page du composant
cible avant de reprendre sans changement un tableau `options` ou un callback shadcn.

## Migrez écran par écran

1. Ajoutez la feuille de style de base moduix et importez-la avant vos surcharges.
2. Commencez par des composants peu couplés, comme `Button`, `Badge`, `Avatar` et `Separator`.
3. Migrez les composants flottants et ceux fondés sur des collections, famille par famille, avec leurs parties de portail et leurs callbacks d’état.
4. Utilisez une [recette](/recipes) uniquement si le flux de l’écran correspond à votre produit.
5. Vérifiez la navigation au clavier, la restitution du focus, les labels et les rôles ARIA importants, puis supprimez l’ancien code source et les styles du composant.

Les responsabilités de l’application doivent rester dans l’application. Les labels, messages de
validation, permissions, appels serveur et parcours produit n’ont pas leur place dans un composant générique
générique. Ark fournit le comportement des primitives ; moduix fournit l’API des composants, les
styles et les valeurs par défaut.

Consultez [Mise à jour et migration](/docs/updating) pour les mises à jour ultérieures du paquet ou
du registre. Lisez [Patrons de composition](/docs/composition-patterns) pour adapter vos composants d’enveloppe
existants.
