# Migration depuis shadcn

moduix reprend ce qui rend shadcn simple à adopter : le code source que vous gardez dans votre projet,
`components.json` et l’installation depuis le registre. Les principales différences sont des noms de
composants cohérents, des API composées dans l’esprit d’Ark et un CSS fondé sur les tokens, qui n’a pas besoin de Tailwind.

Il n’est pas nécessaire de migrer toute l’application d’un coup. Commencez par un écran ou une famille
de composants : pendant la transition, shadcn et moduix peuvent coexister.

## Choisissez comment gérer le code

| Mode moduix | À choisir si | Mises à jour |
| --- | --- | --- |
| Paquet npm | Vous voulez des mises à jour gérées par le gestionnaire de paquets et des imports stables depuis `@moduix/react/*`. | Mettez à jour le paquet. |
| Registre compatible shadcn | Le code source et les styles doivent se trouver dans votre dépôt. | Examinez et appliquez les mises à jour du registre. |

Consultez le [Démarrage rapide](/docs/quick-start) pour la configuration complète. Si vous utilisez
déjà shadcn, conservez son CLI et votre `components.json`, puis ajoutez le registre moduix et les
alias qui y sont indiqués.

## Trouvez le composant équivalent

moduix privilégie le nom de l’interaction sous-jacente plutôt qu’un alias lié au produit.

| Nom shadcn habituel | Utilisez dans moduix | Note de migration |
| --- | --- | --- |
| Accordion | `Accordion` | Même interaction, avec des parties nommées dans un même espace de noms. |
| Alert Dialog | `Dialog` | Définissez `role="alertdialog"` ; aucun alias séparé n’est nécessaire. |
| Avatar | `Avatar` | Placez le fallback et l’image dans les parties `Avatar`. |
| Breadcrumb | `Breadcrumbs` | Nom de famille au pluriel ; conservez les liens sémantiques et l’état de la page courante. |
| Calendar | `DatePicker` | Utilisez la vue calendrier, sans créer une deuxième famille publique. |
| Carousel | `Carousel` | Les contrôles, indicateurs et groupes d’éléments suivent la structure Ark. |
| Collapsible | `Collapsible` | Utilisez l’objet `details` fourni par `onOpenChange` plutôt qu’un callback booléen. |
| Combobox | `Combobox` | L’état de la collection et les valeurs des éléments suivent les contrats Ark. |
| Command | `CommandPalette` | Une interface prête pour la recherche et les commandes, pas un alias de liste générique. |
| Context Menu | `Menu.ContextTrigger` | La même famille `Menu` avec un déclencheur contextuel. |
| Data Table | `Table` + recette Data Table | Conservez le tri, le filtrage et l'état serveur dans le code applicatif. |
| Date Picker | `DatePicker` | Une seule famille composée, pour la saisie de date comme pour le calendrier. |
| Dropdown Menu | `Menu` | Utilisez le chemin habituel avec `Menu.Trigger`. |
| Form | `Field` et `Fieldset` | Gardez la validation et la soumission dans la bibliothèque de formulaires ou l’application. |
| Hover Card | `HoverCard` | Même objectif, avec les détails de positionnement et de cycle de vie d’Ark. |
| Input OTP | `PinInput` | La prise en charge des formulaires natifs et du SSR fait partie du contrat du composant. |
| Progress | `ProgressLinear` ou `ProgressCircular` | Choisissez explicitement la forme visuelle. |
| Resizable | `Splitter` | Les panneaux utilisent des identifiants stables et un état de mise en page explicite. |
| Select | `Select` | Les éléments utilisent une collection Ark plutôt que des objets option ad hoc. |
| Sheet | `Drawer` | Un panneau latéral dont le cycle de vie est aligné sur Dialog. |
| Sidebar | `Sidebar` | Conservez la composition d’une navigation produit adaptative. |
| Sonner / Toast | `Toast` | Une seule surface de notification, dont l’application maîtrise les messages. |
| Tabs | `Tabs` | Même interaction avec des parties composées nommées. |
| Toggle Group | `ToggleGroup` | Utilisez les valeurs des éléments et l’état du groupe définis par le contrat Ark. |
| Tooltip | `Tooltip` | Le déclencheur et le contenu rendu dans un portail restent explicites. |

Il est inutile de chercher un équivalent direct pour Navigation Menu et Menubar. Choisissez `Sidebar`,
`Menu`, `Breadcrumbs` ou des liens ordinaires selon l’interaction recherchée.

## Adaptez les imports

shadcn exporte généralement chaque partie comme un symbole local distinct :

```tsx
import { Dialog, DialogContent, DialogTitle, DialogTrigger } from '@/components/ui/dialog';
```

moduix réunit une famille de composants sous un seul espace de noms :

```tsx
import { Dialog } from '@moduix/react/dialog';

<Dialog>
  <Dialog.Trigger>Open</Dialog.Trigger>
  <Dialog.Backdrop />
  <Dialog.Positioner>
    <Dialog.Content>
      <Dialog.Title>Project settings</Dialog.Title>
    </Dialog.Content>
  </Dialog.Positioner>
</Dialog>;
```

Lors d’une installation avec copie du code source dans le projet, seul le chemin d’import change :

```tsx
import { Dialog } from '@/components/moduix/dialog';
```

Les parties explicites `Backdrop`, `Positioner` et `Content` simplifient la personnalisation du portail
et de la mise en page.

## Adaptez les styles sans tout réécrire

moduix fournit un CSS prêt à l’emploi et des tokens partagés `--moduix-*`. Importez une seule fois la
feuille de style de base, puis personnalisez les tokens sémantiques dans un CSS chargé après elle :

```css title="app.css"
:root {
  --moduix-color-accent: oklch(58% 0.18 260deg);
  --moduix-radius-md: 0.625rem;
}
```

Tailwind peut rester dans l’application pour la mise en page et les classes utilitaires ponctuelles.
Il n’est pas requis par moduix, et il n’est pas nécessaire de convertir chaque utilitaire avant de
remplacer un composant. Les pages de composants répertorient les slots stables, les variables CSS et
les propriétés `className` pour les exceptions locales.

## Adaptez les callbacks d’état au modèle Ark

Les callbacks Ark reçoivent un objet `details`, afin que le contrat puisse évoluer sans arguments
positionnels :

```tsx
<Dialog open={open} onOpenChange={(details) => setOpen(details.open)}>
  {/* parts */}
</Dialog>
```

Les composants fondés sur des collections utilisent aussi des valeurs d’éléments stables et un état de
collection explicite. Consultez la page du composant cible avant de copier tel quel un callback shadcn
ou une structure `option`.

## Migrez par étapes

1. Ajoutez la feuille de style de base et les tokens moduix.
2. Remplacez les composants peu dépendants : Button, Badge, Avatar et Separator.
3. Migrez les overlays et les collections, une famille à la fois, y compris les parties du portail et de l’état.
4. Remplacez les modèles d’écran par des [recettes](/recipes) uniquement lorsque le flux produit correspond.
5. Une fois l’écran validé, supprimez l’ancien code source du composant et ses styles.

Les responsabilités de l’application restent dans l’application : libellés, messages de validation,
permissions, appels serveur et flux produit. Ark fournit le comportement des primitives ; moduix
fournit le contrat du wrapper, les styles et les valeurs par défaut.

Utilisez [Mise à jour et migration](/docs/updating) pour les mises à jour ultérieures du paquet ou du registre, et
[Patrons de composition](/docs/composition-patterns) lorsque vous adaptez des wrappers existants.
