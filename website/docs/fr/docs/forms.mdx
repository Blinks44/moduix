# Formulaires

Moduix fournit des champs accessibles, des contrôles et la participation aux formulaires natifs.
Commencez par `<form>` et ajoutez une bibliothèque d’état uniquement si la validation, les champs
répétés ou le cycle de soumission l’exigent.

## Prise en charge des frameworks

| Approche        | React | Solid | Cas d’usage                                      |
| --------------- | ----- | ----- | ------------------------------------------------ |
| Formulaire natif | Oui  | Oui   | Petits formulaires et validation du navigateur. |
| Formisch        | Oui   | Oui   | Schémas Valibot et état réactif compact.         |
| React Hook Form | Oui   | Non   | Formulaires React privilégiant le non-contrôlé.  |
| TanStack Form   | Oui   | Oui   | État contrôlé explicite et scénarios typés.      |

React Hook Form est volontairement documenté uniquement pour React. Dans Solid, utilisez un
formulaire natif, Formisch ou TanStack Form plutôt qu’une couche de compatibilité pour des hooks React.

## Règles essentielles

1. Entourez un contrôle de `Field` lorsqu’il lui faut un libellé, une aide, une erreur ou un état partagé.
2. Utilisez `Fieldset` pour un groupe lié avec une légende visible.
3. Gardez les libellés visibles et donnez un `name` à chaque contrôle envoyé.
4. Transmettez `invalid`, `required`, `disabled` et `readOnly` au champ ou à la racine Moduix.
5. Ajoutez chaque élément natif requis exactement une fois.

| Composant       | Élément natif du formulaire                                      |
| --------------- | ----------------------------------------------------------------- |
| `Checkbox`      | `HiddenInput`                                                     |
| `RadioGroup`    | `ItemHiddenInput` pour chaque élément composé explicitement      |
| `SegmentGroup`  | `ItemHiddenInput` pour chaque élément composé explicitement      |
| `Select`        | `HiddenSelect`                                                    |
| `Slider`        | `HiddenInput` pour chaque curseur envoyé                         |
| `DateInput`     | `HiddenInput` indexés si une plage utilise des noms distincts    |
| `SignaturePad`  | `HiddenInput` avec une valeur sérialisée par l’application       |
| Autres contrôles Ark avec élément masqué | Le `HiddenInput` correspondant dans la racine |

Ne créez pas un second élément input masqué pour la même valeur. `Combobox` reçoit le nom du
formulaire sur sa racine et ne demande aucun élément masqué supplémentaire.

## Validation et réinitialisation

Conservez les contraintes natives comme `required`, `minLength`, `pattern`, `min` et `max` lorsque
le navigateur gère la validation. Si une bibliothèque affiche les erreurs, ajoutez `noValidate`,
transmettez son résultat à `Field invalid` et rendez un `Field.ErrorText` clair après le cycle choisi.

`type="reset"` et `form.reset()` restaurent les contrôles non contrôlés. Pour les champs contrôlés,
utilisez l’API de réinitialisation de la bibliothèque afin de synchroniser son état et les valeurs Moduix.

Déplacez le focus vers le véritable élément interactif lors d’une soumission invalide : `Input`,
`Textarea`, `Select.Trigger` ou `ComboboxInput`.

## Soumission et erreurs du serveur

Rendez explicites les états prêt, en cours, erreur et réussite. Bloquez les requêtes en double,
conservez les valeurs après un échec et laissez une action claire pour réessayer.

Associez une erreur serveur liée à une valeur au `Field.ErrorText` correspondant. Affichez les
échecs généraux avec `role="alert"`. Les champs répétés doivent utiliser des identifiants stables
pour conserver leurs valeurs, leur focus et leurs erreurs lorsqu’une ligne est retirée.

Les valeurs de `FormData` sont des chaînes ou des objets `File`. Normalisez et validez toujours les
données côté serveur. Pour le comportement Ark sous-jacent, consultez le
[guide des formulaires Ark UI](https://ark-ui.com/docs/guides/forms).
