# Формы

moduix не управляет состоянием формы. Используйте нативный `<form>`, когда достаточно валидации
браузера и `FormData`. Подключайте библиотеку форм, когда нужна более сложная валидация, состояние
полей или сценарии отправки.

## Начните с нативной формы

Сначала выберите нативное состояние формы, если в ней несколько полей и достаточно валидации
браузера. Добавьте каждому элементу управления видимую метку и `name`, задайте нативные ограничения
на самом элементе управления и прочитайте отправленные данные с помощью `new FormData(event.currentTarget)`.
[Рабочий пример нативной формы](#нативная-форма) объединяет обычный Input с Select и Checkbox на базе Ark
без дублирующих скрытых полей ввода.

Добавляйте библиотеку только тогда, когда продукту нужны массивы полей, валидация по схеме или между
полями, контролируемое состояние, используемое в других частях интерфейса, либо жизненный цикл
валидации, который нативные формы не могут выразить достаточно ясно.

## Роль библиотек форм

moduix отвечает за доступную структуру формы: метки, описания, связь сообщений об ошибках с полем,
семантические части элементов управления и нативный элемент управления, нужный для отправки и сброса.
Библиотека форм отвечает за состояние приложения: значения полей, момент валидации, состояние
изменённости и посещения полей, а также сценарий отправки. Не смешивайте эти обязанности.

| Задача | moduix и браузер | Библиотека форм |
| ------ | ---------------- | --------------- |
| Семантика формы | Отрисовывают видимый элемент управления, `name`, метку, описание и нативный элемент. | Не добавляет ещё одно поле ввода для того же значения. |
| Значение и валидация | Применяют нативные ограничения и передают состояние `Field` в дерево элементов управления. | Хранит значения, выбирает валидаторы и предоставляет результаты валидации. |
| Сброс и фокус | Нативный сброс синхронизирует компоненты на базе Ark через их элемент управления формы. | Сбрасывает контролируемое состояние и, если поддерживается, переводит фокус на невалидные поля. |

Это означает, что библиотека дополняет настоящую `<form>`, а не заменяет её. Передавайте текущий
результат валидации библиотеки в `Field invalid` и отрисовывайте сообщение с помощью
`Field.ErrorText`, сохраняя семантические пропсы компонента на его корневом элементе moduix.

## Основные правила

1. Оберните один элемент управления в `Field`, если ему нужны метка, вспомогательный текст, текст
   ошибки или общее состояние `disabled`, `invalid`, `required` и `readOnly`.
2. Используйте `Fieldset`, когда несколько связанных элементов управления используют одну легенду.
3. Оставляйте метки видимыми. Placeholder - это пример, а не замена метке.
4. Добавляйте `name` отправляемым элементам управления.
5. Настраивайте участие в форме через пропсы корневого элемента компонента, например `name`, `form`
   и состояние валидации. moduix отрисовывает обязательное нативное поле ввода для перечисленных ниже
   компонентов.

Поведение в нативной форме:

| Компонент | Поведение |
| --------- | --------- |
| `AngleSlider` | `Root` автоматически отрисовывает нативное поле ввода. |
| `Checkbox` | `Root` автоматически отрисовывает нативное поле ввода. |
| `ColorPicker` | `Root` автоматически отрисовывает нативное поле ввода. |
| `DateInput` | `Root` автоматически отрисовывает нативные поля ввода. |
| `FileUpload` | `Root` автоматически отрисовывает нативное поле ввода. |
| `PinInput` | `Root` автоматически отрисовывает нативное поле ввода. |
| `RadioGroup` | Каждый `Item` автоматически отрисовывает нативное поле ввода. |
| `RatingGroup` | `Root` автоматически отрисовывает нативное поле ввода. |
| `SegmentGroup` | Каждый `Item` автоматически отрисовывает нативное поле ввода. |
| `Select` | `Root` автоматически отрисовывает нативный select. |
| `SignaturePad` | `Root` сериализует пути и автоматически отрисовывает нативное поле ввода. |
| `Slider` | Каждый `Thumb` автоматически отрисовывает нативное поле ввода. |
| `Switch` | `Root` автоматически отрисовывает нативное поле ввода. |
| `TagsInput` | `Root` автоматически отрисовывает нативное поле ввода. |
| `Combobox` | Укажите `name` на корневом элементе; дополнительная часть не требуется. |

Не добавляйте второе скрытое поле ввода. Оно может отправить конфликтующее значение и нарушить
поведение сброса.

Для элементов управления с параметрами, относящимися к форме, сохраняйте конфигурацию на семантическом
корневом элементе:

- `DateInput`: диапазон с `name="date"` отправляет `date[0]` и `date[1]`; используйте
  `names={['start-date', 'end-date']}` для `start-date[0]` и `end-date[1]`.
- `Select`: нативный select по умолчанию сохраняет автозаполнение браузера и прогрессивное улучшение.
  Используйте `nativeFormControl="input"` для очень большой виртуализированной коллекции; он отправляет
  облегчённые скрытые поля ввода и намеренно не предоставляет этих возможностей нативного select.
- `SignaturePad`: значением формы по умолчанию являются SVG-пути, соединённые пробелами. Используйте
  `getFormValue={(paths) => JSON.stringify(paths)}`, когда сервер ожидает JSON-массив.

Для групп, например набора Checkbox, вариантов Radio или нескольких связанных полей ввода, используйте
`Fieldset` с видимой `Fieldset.Legend`. Он предоставляет метку, вспомогательный текст, текст ошибки и
общее состояние на уровне группы; смотрите отдельное [руководство по Fieldset](/docs/fieldset) с
паттернами его композиции.

## Нативная форма

Нативные поля ввода и элементы управления на базе Ark можно отправлять вместе через `FormData`.
Карточка отвечает только за представление; нативная форма по-прежнему управляет отправкой, валидацией
и сбросом.

      .form {

      }

## Валидация, сброс и фокус

Есть два корректных режима валидации. Для простой нативной формы сохраните такие ограничения, как
`required`, `minLength`, `pattern`, `min` и `max`, и позвольте браузеру показать свой интерфейс
валидации. Когда библиотека должна управлять видимыми сообщениями об ошибках, добавьте к форме
`noValidate` и передайте её результат в `Field invalid` вместе с ясным `Field.ErrorText`. Сохраняйте
`Field required` в обоих случаях: компоненты, знающие Ark, наследуют семантическое обязательное
состояние через контекст поля.

Если вы компонуете пользовательский элемент управления не из Ark, самостоятельно примените его
нативное ограничение и состояние `aria-invalid` к фактическому элементу, на который можно перевести
фокус. Не показывайте ошибку только потому, что поле обязательно: показывайте её после того, как
выбранный жизненный цикл валидации обнаружит проблему.

В нативной форме `type="reset"` или `form.reset()` восстанавливает значения элементов управления по
умолчанию. Компоненты на базе Ark синхронизируют своё внутреннее состояние через нативный элемент
управления формы, который отрисовывает moduix. Для контролируемых полей библиотеки вызывайте API
сброса библиотеки вместо того, чтобы полагаться только на сброс DOM, иначе следующий рендер может
восстановить прежнее значение из состояния приложения.

Библиотекам форм нужен ref элемента, на который пользователь может перевести фокус:

- `Input`, `Textarea` или `Field.Select` для нативных элементов управления
- `Select.Trigger` для `Select`
- `Combobox.Input` для `Combobox`

React Hook Form использует этот ref для встроенного перевода фокуса на невалидное поле. TanStack Form
намеренно оставляет управление фокусом приложению, поэтому при необходимости в обработчике
неуспешной отправки переводите фокус на первый отрисованный элемент управления с `aria-invalid`.
В отдельных руководствах по интеграции показаны соответствующие сопоставления значений, blur, сброса
и фокуса.

## Жизненный цикл отправки

Независимо от библиотеки состояния явно обозначайте состояние запроса:

| Состояние | Поведение для пользователя |
| --------- | -------------------------- |
| Готово | Отправка доступна, а валидация не показала преждевременных ошибок. |
| Отправка | Предотвращайте повторные запросы, оставляйте значения видимыми и обозначайте выполняемое действие. |
| Ошибка поля | Прикрепите сообщение сервера к этому полю и переведите фокус, если отправка невалидна. |
| Ошибка формы | Отрисуйте один `role="alert"` рядом с заголовком или действием отправки и сохраните возможность повторить попытку. |
| Успех | Подтвердите завершение, сбрасывайте только при необходимости или перейдите к понятному следующему шагу. |

Значения `FormData` - это строки или объекты `File`. Повторяющиеся имена создают повторяющиеся записи,
неотмеченные нативные Checkbox могут отсутствовать. Читайте повторяющиеся поля с помощью `getAll`,
нормализуйте значения на границе сервера и никогда не считайте тип или валидацию на клиенте достаточным
основанием доверять отправленным данным.

## Повторяющиеся поля и ошибки сервера

Для редактируемого списка, например контактных email-адресов, участников команды или строк заказа,
позвольте выбранной библиотеке форм добавлять, удалять и валидировать элементы. Используйте `Fieldset`
с видимой легендой для группы; каждому элементу всё равно нужны собственные `Field`, метка и сообщение
об ошибке. Ключи должны идентифицировать элемент, а не его текущую позицию, чтобы он сохранял значение,
фокус и ошибку при удалении или изменении порядка соседнего элемента.

Отделяйте ошибки, возвращённые после запроса, от клиентской валидации. Сопоставляйте ошибку конкретного
значения, например уже используемого email-адреса, с `Field.ErrorText` этого поля; ошибку запроса или
прав доступа, не относящуюся к полю, отрисовывайте как `role="alert"` на уровне формы. Сохраняйте
значения пользователя на месте, чтобы он мог их исправить и отправить снова. В руководствах по
интеграции есть компактные рецепты для [React Hook Form](/docs/react-hook-form#повторяющиеся-поля),
[TanStack Form](/docs/tanstack-form#повторяющиеся-поля) и [Formisch](/docs/formisch#повторяющиеся-поля).

Описание поведения базовых примитивов, включая контекст `Field` и синхронизацию нативного сброса,
смотрите в [руководстве Ark UI по формам](https://ark-ui.com/docs/guides/forms).
