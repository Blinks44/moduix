# Формы

moduix не хранит состояние формы. Начните с нативного `<form>`, если достаточно встроенной
валидации браузера и `FormData`. Подключите библиотеку форм, если нужны более сложная валидация,
состояние полей или особый сценарий отправки.

## Нативные формы

Начните с нативной формы, если в ней немного полей и встроенной валидации достаточно. У каждого
элемента управления должна быть видимая метка и `name`; ограничения задавайте на самом элементе, а
данные читайте через `new FormData(event.currentTarget)`. В [рабочем примере нативной формы](#нативная-форма)
обычный `Input` сочетается с `Select` и `Checkbox` на базе Ark без дублирующих скрытых полей.

Библиотека нужна, только если требуются массивы полей, валидация по схеме или между полями,
контролируемое состояние для других частей интерфейса или сценарий валидации, который нативная форма
не позволяет выразить достаточно ясно.

## Библиотеки форм

moduix отвечает за доступную структуру формы: метки, описания, связь сообщений об ошибках с полями,
семантические части элементов управления и нативный элемент формы, нужный для отправки и сброса.
Библиотека форм управляет состоянием приложения: значениями полей, моментом валидации, состояниями
изменённости и посещения полей, а также сценарием отправки. Не смешивайте эти обязанности.

| Область | moduix и браузер | Библиотека форм |
| ------- | ---------------- | --------------- |
| Семантика формы | Отрисовывают видимый элемент управления, `name`, метку, описание и связанный нативный элемент формы. | Не добавляет ещё одно поле ввода для того же значения. |
| Значение и валидация | Применяют нативные ограничения и передают состояние `Field` в дерево элементов управления. | Хранит значения, выбирает валидаторы и предоставляет результаты валидации. |
| Сброс и фокус | Нативный сброс синхронизирует компоненты на базе Ark через их элемент формы. | Сбрасывает контролируемое состояние и, если поддерживается, переводит фокус на невалидные поля. |

Иными словами, библиотека дополняет настоящую `<form>`, а не заменяет её. Передавайте текущий
результат валидации в проп `invalid` компонента `Field` и выводите сообщение с помощью
`Field.ErrorText`. Семантические свойства, например `name`, `required` и `disabled`, оставляйте на
корневом элементе компонента moduix.

## Основные правила

1. Используйте `Field` вокруг одного элемента управления, если ему нужны метка, вспомогательный
   текст, текст ошибки или общее состояние `disabled`, `invalid`, `required` и `readOnly`.
2. Используйте `Fieldset`, когда нескольким связанным элементам управления нужны одна легенда и
   общее состояние.
3. Оставляйте метки видимыми. Плейсхолдер - это подсказка, а не замена метке.
4. Добавляйте `name` каждому элементу управления, который должен попасть в отправку формы.
5. Передавайте настройки формы через семантический корневой элемент компонента, например `name`,
   `form` и состояние валидации. Для перечисленных ниже компонентов moduix сам добавляет нужный
   элемент формы.

Явные Ark-части для форм:

| Компонент | Участие в отправке формы |
| --------- | ----------------------- |
| `AngleSlider` | Добавьте `HiddenInput` внутрь корня. |
| `Checkbox` | Добавьте `HiddenInput` внутрь корня. |
| `ColorPicker` | Добавьте `HiddenInput` внутрь корня. |
| `DateInput` | Добавьте индексированный `HiddenInput` для каждой отправляемой даты. |
| `FileUpload` | Добавьте `HiddenInput` внутрь корня. |
| `PinInput` | Добавьте `HiddenInput` внутрь корня. |
| `RadioGroup` | Добавьте `ItemHiddenInput` в каждый явно собранный `Item`. |
| `RatingGroup` | Добавьте `HiddenInput` внутрь корня. |
| `SegmentGroup` | Добавьте `ItemHiddenInput` в каждый явно собранный `Item`. |
| `Select` | Добавьте `HiddenSelect` внутрь корня. |
| `SignaturePad` | Добавьте `HiddenInput` со значением из контекста. |
| `Slider` | Добавьте `HiddenInput` внутрь каждого отправляемого `Thumb`. |
| `Switch` | Добавьте `HiddenInput` внутрь корня. |
| `TagsInput` | Добавьте `HiddenInput` внутрь корня. |
| `Combobox` | Передайте `name` в корневой элемент; дополнительные части не нужны. |

Добавляйте каждую часть формы ровно один раз. Дубликат может отправить конфликтующее значение.

Для элементов управления с параметрами, связанными с формой, оставляйте настройки на семантическом
корневом элементе:

- `DateInput`: для диапазона используйте `HiddenInput index={0} name="start-date"` и
  `HiddenInput index={1} name="end-date"`, если датам нужны разные имена при отправке.
- `Select`: `HiddenSelect` сохраняет автозаполнение браузера, нативную валидацию и постепенное
  улучшение. Для виртуализированной коллекции, которая не может отрисовать нативные options,
  интеграцией с формой управляет приложение.
- `SignaturePad`: `HiddenInput` требует явную строку `value`. Получите `paths` через
  `useSignaturePadContext()` и сериализуйте их в формате, который ожидает сервер.

Для группы флажков, вариантов Radio или других связанных полей используйте `Fieldset` с видимой
`Fieldset.Legend`. Он предоставляет метку, вспомогательный текст, текст ошибки и общее состояние
группы. В [руководстве по Fieldset](/docs/fieldset) показаны варианты композиции.

## Валидация и сброс

Есть два рабочих варианта валидации. Для простой нативной формы сохраните такие ограничения, как
`required`, `minLength`, `pattern`, `min` и `max`, и позвольте браузеру показать свой интерфейс
валидации. Если видимыми сообщениями об ошибках должна управлять библиотека, добавьте к форме
`noValidate`, передавайте результат валидации в проп `invalid` компонента `Field` и выводите понятное
сообщение через `Field.ErrorText`. В обоих случаях оставляйте `required` на `Field`: компоненты на
базе Ark наследуют семантику обязательного поля через контекст. Этот выбор также определяет, как
обрабатывать ошибки и управлять фокусом.

Если вы создаёте собственный элемент управления не на базе Ark, самостоятельно примените его
нативное ограничение и состояние `aria-invalid` к фактическому элементу, на который можно перевести
фокус. Не показывайте ошибку только потому, что поле обязательное: выводите её после того, как
выбранный сценарий валидации обнаружит проблему.

В нативной форме `type="reset"` или `form.reset()` восстанавливает исходные значения элементов
управления. Компоненты на базе Ark синхронизируют внутреннее состояние через явно добавленную
нативную часть формы. Для полей, управляемых библиотекой, вызывайте её API сброса, а не полагайтесь
только на сброс DOM: иначе следующий рендер может вернуть старое значение из состояния приложения.

Библиотекам форм нужен `ref` элемента, на который следует перевести фокус:

- `Input`, `Textarea` или `Field.Select` для нативных элементов управления
- `Select.Trigger` для `Select`
- `Combobox.Input` для `Combobox`

React Hook Form использует этот `ref`, чтобы автоматически перевести фокус на первое невалидное поле.
TanStack Form намеренно оставляет управление фокусом приложению. Если это нужно, в обработчике
неуспешной отправки переводите фокус на первый отрисованный элемент с `aria-invalid`. В руководствах
по интеграции показано, как сопоставить значения, blur, сброс и фокус.

## Отправка

Независимо от выбранной библиотеки явно обозначайте состояние запроса:

| Состояние | Поведение для пользователя |
| --------- | -------------------------- |
| Готово | Кнопка отправки доступна, а ошибки валидации не показываются раньше времени. |
| Отправка | Блокируйте повторные запросы, оставляйте значения видимыми и обозначайте выполняемое действие. |
| Ошибка поля | Покажите сообщение сервера у нужного поля и переведите на него фокус, если отправка не удалась. |
| Ошибка формы | Выведите один `role="alert"` рядом с заголовком или кнопкой отправки и оставьте возможность повторить попытку. |
| Успешно | Подтвердите завершение, сбрасывайте форму только при необходимости или ведите пользователя к понятному следующему шагу. |

Значения `FormData` - это строки или объекты `File`. Повторяющиеся имена создают несколько записей,
а неотмеченные нативные флажки могут отсутствовать. Читайте повторяющиеся поля с помощью `getAll`,
нормализуйте значения на границе сервера и не считайте клиентскую типизацию или валидацию достаточным
основанием доверять отправленным данным.

## Списки и ошибки сервера

Для редактируемого списка, например контактных адресов электронной почты, участников команды или строк
заказа, позвольте выбранной библиотеке форм добавлять, удалять и проверять элементы. Используйте
`Fieldset` с видимой легендой для группы; каждому элементу всё равно нужны собственные `Field`, метка
и сообщение об ошибке. Ключи должны идентифицировать сам элемент, а не его текущую позицию, чтобы при
удалении или перестановке соседнего элемента сохранялись его значение, фокус и ошибка.

Отделяйте ошибки, возвращённые после запроса, от клиентской валидации. Ошибку конкретного значения,
например уже занятого адреса электронной почты, показывайте через `Field.ErrorText` этого поля; ошибку
запроса или прав доступа, не связанную с конкретным полем, выводите на уровне формы с помощью
`role="alert"`. Сохраняйте введённые значения, чтобы пользователь мог исправить их и отправить форму
снова. В руководствах по интеграции есть компактные рецепты для
[React Hook Form](/docs/react-hook-form#повторяющиеся-поля), [TanStack Form](/docs/tanstack-form#повторяющиеся-поля)
и [Formisch](/docs/formisch#повторяющиеся-поля).

Описание поведения базовых примитивов, включая контекст `Field` и синхронизацию нативного сброса,
смотрите в [руководстве Ark UI по формам](https://ark-ui.com/docs/guides/forms).
