# Паттерны композиции

moduix не скрывает композицию Ark. Вместо одного большого набора пропов большинство компонентов предоставляет
корневую часть с состоянием и отдельные части для семантики, компоновки и стилей.

Такой подход задаёт понятную последовательность настройки:

- используйте поставляемые части напрямую;
- реэкспортируйте их под именами вашего продукта;
- оборачивайте только те части, которым нужны повторяющиеся стили или компоновка.

Эти приёмы одинаково работают и с `@moduix/react`, и с исходным кодом из реестра.

## Выберите способ установки

Выберите npm-пакет, если хотите получать обновления через менеджер пакетов, импортировать компоненты из
`@moduix/react/*` и стили из `@moduix/react/style.css`.

Выберите реестр `shadcn`, если хотите хранить исходный код компонентов в приложении. Он добавит
выбранный компонент и требуемые ему стили, иконки и утилиты moduix в проект, поэтому их можно изменять
напрямую и импортировать из `@/components/moduix/*`.

Компоненты из исходного кода не обновляются вместе с пакетом. Когда выйдет новая версия moduix, добавьте её через
`shadcn`, а затем проверьте и объедините получившийся diff. Одноразовая настройка реестра и команды для компонентов описаны в
[Быстром старте](/docs/quick-start#install-with-the-shadcn-cli).

## Дерево частей

Прежде чем создавать обёртки, изучите дерево частей на странице компонента. Применяйте `className`, CSS-переменные,
`data-slot` и атрибуты состояния Ark к тем частям, которым они действительно принадлежат.

Корневые экспорты, такие как `Popover`, `Tooltip` и `Select`, — сокращённая форма `*.Root`. Корни
всплывающих компонентов и компонентов, похожих на диалоги, автоматически отрисовывают поддерево оверлея
через портал, поэтому структура остаётся видимой без отдельной обёртки `Portal`.

Например:

```text
Dialog / Dialog.Root
├─ Dialog.Trigger
├─ Overlay subtree (automatically portalled)
│  ├─ Dialog.Backdrop
│  └─ Dialog.Positioner
│     └─ Dialog.Content
│        ├─ Dialog.Title
│        ├─ Dialog.Description
│        └─ Dialog.CloseTrigger
```

Используйте `portalled={false}` для отрисовки в потоке и `portalRef` для пользовательского контейнера,
когда компонент поддерживает эти пропы. Используйте `Dialog.RootProvider` как альтернативную точку входа
для состояния, если объект состояния находится за пределами отрисованного поддерева.

## Структурные части

Не каждый примитив предоставляет все перечисленные ниже части. Ориентируйтесь на анатомию на странице компонента и
оставляйте видимыми те из них, которые продукту может понадобиться переопределить.

| Часть | Ответственность |
| --- | --- |
| `Backdrop` | Обеспечивает модальное разделение и нацеливание для взаимодействий вне компонента. |
| `Positioner` | Отвечает за размещение в области просмотра или относительно якоря, а также за прокрутку. |
| `Content` | Отрисовывает интерактивную поверхность и получает атрибуты состояния. |
| `Arrow` | Соединяет содержимое всплывающего окна, привязанного к якорю, с его триггером, если примитив поддерживает эту часть. |

Не скрывайте эти узлы в обёртках продукта, если только контракт продукта намеренно не убирает точки их
переопределения.

## `asChild`

Используйте `asChild`, когда DOM-узлом должен владеть существующий семантический элемент, а часть moduix лишь
подключает к нему своё поведение.

```tsx
import { Button } from '@moduix/react/button';
import { Popover } from '@moduix/react/popover';
// shadcn copy-owned: import { Button } from '@/components/moduix/button';
// shadcn copy-owned: import { Popover } from '@/components/moduix/popover';

export function FiltersPopover() {
  return (
    <Popover positioning={{ gutter: 8 }}>
      <Popover.Trigger asChild>
        <Button variant="outline">Filters</Button>
      </Popover.Trigger>
      <Popover.Positioner>
        <Popover.Content>Choose one or more filters.</Popover.Content>
      </Popover.Positioner>
    </Popover>
  );
}
```

Оставляйте один семантический дочерний элемент, который может принять пропы Ark. Если дочерний компонент не передаёт
`ref`, обработчики событий или атрибуты, `asChild` не сработает корректно.

## `ids`

В большинстве случаев связи создаются автоматически. Передавайте `ids` только когда двум примитивам нужно сослаться
на один триггер или узел описания, а не задавайте ARIA-связи вручную.

```tsx
import { Avatar } from '@moduix/react/avatar';
import { Tooltip } from '@moduix/react/tooltip';
import { useId } from 'react';

export function AssigneeTooltip() {
  const id = useId();

  return (
    <Tooltip ids={{ trigger: id }}>
      <Tooltip.Trigger asChild>
        <Avatar ids={{ root: id }}>
          <Avatar.Fallback name="Sam Ortiz" />
        </Avatar>
      </Tooltip.Trigger>
      <Tooltip.Body>Sam Ortiz is online</Tooltip.Body>
    </Tooltip>
  );
}
```

Так Ark сам формирует связи для доступности, а вам не приходится дублировать атрибуты `aria-*`.

## Сначала реэкспорт

Если продукту нужны более короткие импорты или собственный API, начните с реэкспорта, а не с новых абстракций. Он
сохраняет исходное поведение и даёт приложению стабильный локальный API.

```tsx
import { Dialog as ModuixDialog } from '@moduix/react/dialog';
// shadcn copy-owned: import { Dialog as ModuixDialog } from '@/components/moduix/dialog';

export const Dialog = ModuixDialog;
export const DialogTrigger = ModuixDialog.Trigger;
export const DialogBackdrop = ModuixDialog.Backdrop;
export const DialogPositioner = ModuixDialog.Positioner;
export const DialogContent = ModuixDialog.Content;
export const DialogTitle = ModuixDialog.Title;
export const DialogDescription = ModuixDialog.Description;
export const DialogCloseTrigger = ModuixDialog.CloseTrigger;
```

Это самый безопасный путь настройки:

- потребители импортируют из слоя продукта, а не напрямую из `@moduix/react/*` или
  `@/components/moduix/*`;
- поведение Ark остаётся нетронутым;
- переход от использования пакета к установке с исходным кодом остаётся простым;
- обёртки можно добавить позже только там, где они действительно нужны.

## Контракт продукта

Добавляйте контракт продукта только той части, которая отвечает за это решение. Локальный `Dialog` становится
полной границей продукта: пользователь импортирует один компонент и получает из него `Dialog.Trigger`,
`Dialog.Content` и остальные части. Внутри небольшой контракт `tone` получает только поверхность диалога, потому
что именно она отвечает за его визуальное оформление.

    </Tab>

Теперь пользователь импортирует только компонент продукта:

```tsx
import { Dialog } from '@/components/ui/dialog';

export function DeleteProjectDialog() {
  return (
    <Dialog>
      <Dialog.Trigger>Delete project</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content tone="danger">
          <Dialog.Header>
            <Dialog.Title>Delete this project?</Dialog.Title>
            <Dialog.CloseIcon />
            <Dialog.Description>This cannot be undone.</Dialog.Description>
          </Dialog.Header>
          <Dialog.Footer>
            <Dialog.CloseTrigger>Cancel</Dialog.CloseTrigger>
          </Dialog.Footer>
        </Dialog.Content>
      </Dialog.Positioner>
    </Dialog>
  );
}
```

Корневая часть продукта сохраняет полный API moduix. Её собственный `Dialog.Content` передаёт `ref`, `className` и
все существующие пропы содержимого. Атрибут `data-dialog-tone` служит хуком стилей продукта: CSS связывает его с
публичными переменными диалога, не копируя стили компонента.

Сохраняйте дерево частей явным: `Dialog.Backdrop`, `Dialog.Positioner` и `Dialog.Content` по-прежнему
наглядно показывают, где живут поведение оверлея и стили. Добавляйте обёртку только для повторяющегося
решения продукта, а не ради разового класса.

## Внешнее состояние

Выносите состояние за пределы дерева только когда меняется его владелец; объекты `details` Ark оставляйте без
изменений. Например, для состояния открытия диалога по-прежнему используйте `onOpenChange(details)` и
`details.open`.

Используйте хелперы состояния компонента, только если состояние должно жить за пределами отрисованного поддерева:

- `Component.Context` для разового чтения в строке;
- `useComponentContext()` внутри потомков, уже находящихся под корневой частью;
- `useComponent()` вместе с `Component.RootProvider`, когда состояние создаётся за пределами
  отрисованного дерева.

```tsx
import { Dialog, useDialog } from '@moduix/react/dialog';

export function DialogFromExternalState() {
  const dialog = useDialog();

  return (
    <Dialog.RootProvider value={dialog}>
      <Dialog.Trigger>Open dialog</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content>State is owned by useDialog().</Dialog.Content>
      </Dialog.Positioner>
    </Dialog.RootProvider>
  );
}
```

Не отрисовывайте `Root` и `RootProvider` для одного экземпляра состояния.

## Как выбрать уровень

- Нужна только возможность использования? Оставайтесь на поставляемых частях.
- Нужны пути импорта продукта? Сначала повторно экспортируйте.
- Нужна повторяющаяся визуальная система продукта? Оборачивайте конкретные части, отвечающие за неё.
- Нужно другое поведение? Используйте явное дерево частей вместо того, чтобы придумывать новые пропы
  верхнего уровня.
