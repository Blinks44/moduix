# Паттерны композиции

`moduix` оставляет модель композиции Ark явной. Большинство компонентов состоит из корневого элемента,
который управляет состоянием, и отдельных частей, отвечающих за структуру, семантику и стили. Поэтому
понятно, какой слой за что отвечает, а способ настройки компонента остаётся предсказуемым:

- используйте готовые части напрямую;
- реэкспортируйте их из слоя продукта;
- оборачивайте только те части, которым нужны повторяющиеся стили или компоновка продукта.

Один и тот же подход работает с `@moduix/react` и с исходным кодом, скопированным из реестра.

## Выберите способ установки

Выберите npm-пакет, если хотите получать обновления через менеджер пакетов. Компоненты импортируются из
`@moduix/react/*`, а общие стили из `@moduix/react/style.css`.

Выберите реестр `shadcn`, если хотите хранить исходный код компонентов в приложении. При добавлении он
копирует выбранный компонент и необходимые ему стили, иконки и утилиты moduix в проект. После этого код
можно менять напрямую, а компоненты импортировать из `@/components/moduix/*`.

Компоненты, исходный код которых хранится в приложении, не получают обновления пакета автоматически. Когда
выходит новая версия moduix, снова добавьте компонент через `shadcn`, проверьте получившийся diff и внесите
нужные изменения. Одноразовая настройка реестра и команды для компонентов описаны в [Быстром старте](/docs/quick-start#установить-через-shadcn-cli).

## Используйте дерево частей

Прежде чем создавать обёртки, изучите дерево частей на странице компонента. Применяйте `className`, CSS-переменные,
`data-slot` и атрибуты состояния Ark к тем частям, которым они действительно принадлежат.

Корневые экспорты, такие как `Popover`, `Tooltip` и `Select`, являются сокращённой формой `*.Root`. Для диалогов
и всплывающих компонентов корневой компонент автоматически помещает поддерево оверлея в портал, поэтому структура
остаётся явной и отдельная обёртка `Portal` не нужна.

Например:

```text
Dialog / Dialog.Root
├─ Dialog.Trigger
├─ Поддерево оверлея (автоматически переносится в портал)
│  ├─ Dialog.Backdrop
│  └─ Dialog.Positioner
│     └─ Dialog.Content
│        ├─ Dialog.Title
│        ├─ Dialog.Description
│        └─ Dialog.CloseTrigger
```

Используйте `portalled={false}` для отрисовки в месте расположения компонента, а `portalRef` для своего контейнера,
если компонент поддерживает эти пропы. Используйте `Dialog.RootProvider`, когда объект состояния создаётся за
пределами отрисованного дерева.

## Структурные части

Не каждый примитив предоставляет все перечисленные ниже части. Сначала изучите анатомию на странице компонента,
а затем оставляйте видимыми те части, которые продукту может понадобиться переопределить.

| Часть         | Ответственность                                                                  |
| ------------- | ------------------------------------------------------------------------------- |
| `Backdrop`    | Отделяет модальную поверхность от остальной страницы и принимает взаимодействия за её пределами. |
| `Positioner`  | Отвечает за размещение в области просмотра или относительно якоря, а также за прокрутку.          |
| `Content`     | Отрисовывает интерактивную поверхность и получает атрибуты состояния.                             |
| `Arrow`       | Соединяет привязанное к якорю содержимое всплывающего окна с триггером, если примитив поддерживает эту часть. |

Не прячьте эти узлы внутри обёрток продукта, если только контракт продукта намеренно не убирает точки их
переопределения.

## `asChild`

Используйте `asChild`, когда существующий семантический элемент должен стать DOM-узлом, а часть moduix должна
только добавить ему своё поведение.

```tsx
import { Button } from '@moduix/react/button';
import { Popover } from '@moduix/react/popover';
// shadcn copy-owned: import { Button } from '@/components/moduix/button';
// shadcn copy-owned: import { Popover } from '@/components/moduix/popover';

export function FiltersPopover() {
  return (
    <Popover positioning={{ gutter: 8 }}>
      <Popover.Trigger asChild>
        <Button variant="outline">Filters</Button>
      </Popover.Trigger>
      <Popover.Positioner>
        <Popover.Content>Choose one or more filters.</Popover.Content>
      </Popover.Positioner>
    </Popover>
  );
}
```

Оставляйте один семантический дочерний элемент, который может принять пропы Ark. Если дочерний компонент не
передаёт `ref`, обработчики событий или атрибуты, `asChild` не будет работать корректно.

## `ids`

В большинстве случаев библиотека создаёт связи сама. Передавайте `ids`, если двум примитивам нужно согласовать
стабильный идентификатор, например использовать один и тот же элемент в качестве триггера. Не задавайте связи
ARIA вручную.

```tsx
import { Avatar } from '@moduix/react/avatar';
import { Tooltip } from '@moduix/react/tooltip';
import { useId } from 'react';

export function AssigneeTooltip() {
  const id = useId();

  return (
    <Tooltip ids={{ trigger: id }}>
      <Tooltip.Trigger asChild>
        <Avatar ids={{ root: id }}>
          <Avatar.Fallback name="Sam Ortiz" />
        </Avatar>
      </Tooltip.Trigger>
      <Tooltip.Body>Sam Ortiz is online</Tooltip.Body>
    </Tooltip>
  );
}
```

Так связи для доступности остаются под управлением Ark, и вам не приходится вручную дублировать атрибуты `aria-*`.

## Сначала реэкспортируйте

Если продукту нужны короткие пути импорта или собственный API, начните с реэкспортов, а не с новых абстракций.
Реэкспорты сохраняют исходное поведение и дают приложению стабильный локальный API.

```tsx
import { Dialog as ModuixDialog } from '@moduix/react/dialog';
// shadcn copy-owned: import { Dialog as ModuixDialog } from '@/components/moduix/dialog';

export const Dialog = ModuixDialog;
export const DialogTrigger = ModuixDialog.Trigger;
export const DialogBackdrop = ModuixDialog.Backdrop;
export const DialogPositioner = ModuixDialog.Positioner;
export const DialogContent = ModuixDialog.Content;
export const DialogTitle = ModuixDialog.Title;
export const DialogDescription = ModuixDialog.Description;
export const DialogCloseTrigger = ModuixDialog.CloseTrigger;
```

Это самый безопасный способ расширения:

- потребители импортируют из слоя продукта, а не напрямую из `@moduix/react/*` или `@/components/moduix/*`;
- поведение Ark не меняется;
- переход от пакета к версии с исходным кодом в приложении остаётся простым;
- обёртки можно добавить позже только там, где они действительно нужны.

## Добавьте контракт продукта

Добавляйте продуктовый контракт только той части, которая отвечает за соответствующее решение. Локальный `Dialog`
становится полноценной границей продукта: потребитель импортирует один компонент и использует его `Dialog.Trigger`,
`Dialog.Content` и остальные части. Внутри обёртки небольшой контракт `tone` добавляется только к поверхности
диалога, потому что именно она отвечает за визуальное решение.

    </Tab>

Теперь потребитель импортирует только компонент продукта:

```tsx
import { Dialog } from '@/components/ui/dialog';

export function DeleteProjectDialog() {
  return (
    <Dialog>
      <Dialog.Trigger>Delete project</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content tone="danger">
          <Dialog.Header>
            <Dialog.Title>Delete this project?</Dialog.Title>
            <Dialog.CloseIcon />
            <Dialog.Description>This cannot be undone.</Dialog.Description>
          </Dialog.Header>
          <Dialog.Footer>
            <Dialog.CloseTrigger>Cancel</Dialog.CloseTrigger>
          </Dialog.Footer>
        </Dialog.Content>
      </Dialog.Positioner>
    </Dialog>
  );
}
```

Корневой компонент продукта сохраняет весь API moduix. Его `Dialog.Content` передаёт `ref`, `className` и все
существующие пропы содержимого. Атрибут `data-dialog-tone` служит хуком стилей продукта, а CSS связывает его с
публичными переменными диалога, не копируя стили компонента.

Сохраняйте дерево частей явным: `Dialog.Backdrop`, `Dialog.Positioner` и `Dialog.Content` по-прежнему показывают,
где находятся поведение оверлея и стили. Добавляйте обёртку только для повторяющегося решения продукта, а не ради
разового класса.

## Состояние вне дерева

Выносите состояние за пределы дерева только тогда, когда меняется место его владения, а объекты `details` Ark
оставляйте без изменений. Например, состояние открытия диалога по-прежнему использует `onOpenChange(details)`,
а текущее значение читается из `details.open`.

Используйте API состояния компонента в зависимости от того, где к нему нужен доступ:

- `Dialog.Context` для разового чтения в дереве рендера;
- `useDialogContext()` внутри переиспользуемых потомков, уже находящихся под корневой частью;
- `useDialog()` вместе с `Dialog.RootProvider`, когда состояние создаётся за пределами отрисованного дерева.

```tsx
import { Dialog, useDialog } from '@moduix/react/dialog';

export function DialogFromExternalState() {
  const dialog = useDialog();

  return (
    <Dialog.RootProvider value={dialog}>
      <Dialog.Trigger>Open dialog</Dialog.Trigger>
      <Dialog.Backdrop />
      <Dialog.Positioner>
        <Dialog.Content>State is owned by useDialog().</Dialog.Content>
      </Dialog.Positioner>
    </Dialog.RootProvider>
  );
}
```

Не отрисовывайте `Root` и `RootProvider` для одного экземпляра состояния.

## Выберите уровень композиции

- Нужен только стандартный способ использования? Оставайтесь на готовых частях.
- Нужны собственные пути импорта? Сначала сделайте реэкспорт.
- Нужны повторяющиеся визуальные решения продукта? Оборачивайте конкретные части, которые за них отвечают.
- Нужно изменить поведение? Используйте явное дерево частей вместо новых пропов верхнего уровня.
